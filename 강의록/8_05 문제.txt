[문제]
이러한 문제가 발생한 기술적 원인(직접 연계의 한계점)을 작성하고, 이를 해결하기 위해 도입해야 하는 연계 미들웨어 방식을 제시하시오. 

DB에 직접 연결하는 방식은

시스템 간 강한 결합(Tight Coupling) 이 발생한다.

따라서 이를 해결하기 위해 EAI(Enterprise Application Integration) 또는 ESB(Enterprise Service Bus) 와 같은 연계 미들웨어 방식을 도입한다.

 전체 연계 설계의 기초가 되며, 이후 작성되는 인터페이스 정의서와 연계 프로그램 개발의 기준이 된다.
 - 연계 데이터 식별이 제대로 이루어지지 않을 경우, 송수신 시스템 간 데이터 구조 및 코드가 불일치하고 오류가 발생할 수 있다. 즉 정확하고 안정적인 데이터 교환을 보장하고 데이터의 정합성을 지키기 위해서 식별 과정이 반드시 필요하다.

[문제 4] 데이터 변환 및 매핑(Mapping)의 개념과 필요성

[예시 상황]

송신 시스템(쇼핑몰): {"name": "홍길동"}

수신 시스템(ERP): {"userName": "홍길동"}

 - 매핑은 송수신 시스템간 같은 의미로 사용되는 코드가 서로 코드명이 다른 경우, 이러한 데이터를 연결하여 변경을 자유롭게 하는 과정을 의미한다. 
(서로 다른 시스템 간에 의미가 같은 데이터 항목을 서로 연결해주는 작업이다.)

 - 송신 시스템에서는 이름에 대한 코드(컬럼명)가 name이지만, 수신 시스템에서는 userName으로 되어 있어서, 그대로 연동하게 되면 데이터 컬럼명의 불일치로 인해 제대로 수신이 이루어지지 않으므로, 매핑 테이블을 통해 name을 userName으로 변경하여 데이터를 수신해야 한다. 
(각 시스템마다 사용하는 컬럼명/속성명이 다르기 때문에 수신하는 측에서 인식하지 못하거나 저장 오류가 발생한다.
데이터를 변환 및 일치시켜 수신측에 전달해야 한다.)

[문제 6] 이기종 시스템 직접 연결 시 발생하는 구조적 문제 및 해결책
A 기업은 온라인 쇼핑몰(REST API 기반)과 기존 ERP 시스템(FTP 및 전용 파일 포맷 사용)을 직접 연결(Point-to-Point)하여 주문 데이터를 연동하려고 한다. 이때 연계 서버(Integration Server) 없이 직접 연동할 경우 발생할 수 있는 유지보수 및 확장성 측면의 문제점을 설명하고, 중계자 역할을 하는 연계 서버를 도입했을 때 얻는 구조적 이점을 제시하시오.

DB에 직접 연결하는 방식은 시스템간 결합도가 높아, 연계 대상 시스템의 변경이 모든 연계 모듈에 직접적인 영향을 미치고 중앙 제어가 불가능하다. 따라서 유지보수 및 확장 시 모든 코드를 전부 조정해야 하는 문제가 생긴다.
(높은 결합도 및 유지보수 난이도 증가 / 시스템 확장성 저해)

 - 따라서 연계 서버를 연결하면 프로토콜, 데이터 형식 변환을 연계 서버가 담당하므로 시스템은 자신의 본래 업무 로직에만 집중할 수 있고 시스템간 결합도가 하락하여(느슨한 결합) 유지보수에 용이하고 확장성이 생겨 유기적인 프로그램 관리를 진행할 수 있다.
 - 추가로 중앙 집중식 통합 관리가 되므로 연계 서버가 메시지 라우팅, 인증, 암호화 및 오류 재처리를 통합 수행하여 새로운 시스템 연계 시 연계 서버의 어댑터 설정 변경만으로 손쉽게 확장이 가능하다.

[문제 7] 연계 방식(실시간 vs 배치) 선택 및 트레이드오프 분석
대용량 사용자를 보유한 금융 시스템에서 '실시간(Real-time) API 연동'과 '주기적 일괄 처리(Batch) 연동'을 적절히 혼용하려 한다. 실시간 처리와 배치 처리를 결정할 때 고려해야 할 핵심 요소 2가지를 설명하고, 모든 연계를 실시간 방식으로 처리했을 때 운영 DB 및 네트워크에 미치는 부작용을 기술하시오.

 - 데이터 적시성 : 즉각적인 결과 확인이 필요한 업무는 실시간 방식을, 시차 반영이 허용되는 업무는 배치 방식을 선택한다.
 - 네트워크 부하 : 처리하려는 데이터의 건수와 크기를 고려하여, 대용량 트랜잭션이 발생할 경우 운영 DB 부하 완화를 위해 배치 처리를 선택한다.

전체를 실시간 처리로 선택했을 때의 부작용
 - 수십만 ~ 수백만 건의 연계 데이터 요청이 순간적으로 몰릴 경우, 운영 DB의 대량의 트랜잭션과 락이 발생하여 DB 성능 저하 및 메모리 부족 현상이 발생한다.
 또한 네트워크 과부하로 인해 연계 타임아웃 오류가 빈번해지며 전체 서비스 불능 상태에 빠질 수 있다.

[문제 8] 인터페이스 테이블(I/F Table)의 임시 저장소 역할과 트랜잭션 보장
송신 시스템에서 수신한 연계 데이터를 수신측 운영 DB의 업무 테이블에 직접(Direct) INSERT 하지 않고, 중간 저장 영역인 인터페이스 테이블(I/F Table)을 거쳐 단계적으로 반영하는 이유를 '데이터 정합성' 및 '오류 복구(재처리)' 관점에서 논하시오.

 - 데이터 정합성 보장 : 수신된 데이터가 업무 DB의 스키마 및 업무 규칙을 준수하는지 검증하는 버퍼  역할을 한다. 중간 검증 과정 없이 직접 적재 시 잘못된 포맷이나 코드 값으로 인해 기존 업무 DB의 데이터 오염을 초래할 수 있다.
 - 오류 복구 및 트랜잭션 독립성 : 수신측 업무 DB 적재 로직 중 예외가 발생하더라도, 인터페이스 테이블에 원래 전달받은 데이터 원본과 원천 로그가 보존되어 있으므로 원인 분석이 용이하다.

[문제 9] 연계 과정에서의 로그(Log) 설계와 장기 추적성
장애 추적을 위해 연계 서버에서 모든 송수신 내역을 로그로 기록하고 있다. 단순 성공/실패 여부만 기록하는 로그 수준을 넘어, 분산 환경에서 특정 연계 건의 전체 이동 경로를 단일 ID로 추적하기 위해 도입해야 하는 로그 기록 요소를 설명하고, 로그가 SLA(Service Level Agreement) 준수 검증에 어떻게 활용될 수 있는지 서술하시오.

 - 추적성을 위한 로그 요소 : 고유 Trace ID를 발급하여 송신 -> 연계 서버 -> 수신 시스템으로 이동하는 전체 흐름 동안 유지하고, 각 단계별 타임스탬프 및 처리 상태를 함께 기록해야 한다.
 - SLA 준수 검증 활용 : 로그에 기록된 '송신 시작 시간'과 '수신 시스템 업무 DB 반영 완료 시간' 간의 차이를 분석하여 연계 구간별 지연시간을 측정한다. 속도를 만족하는지 검증하고, 처리 지연을 유발하는 병목구간을 찾아내어 시스템 구조 개선의 근거로 활용할 수 있다.

[문제 10] 이벤트 기반 통합(Event-driven Integration)과 메시지 큐 활용
온라인 쇼핑몰에서 고객이 '주문 완료'를 할 때, 재고 차감, 결제, 배송 요청, SMS 발송, 알림톡 전송 등의 연쇄 작업이 일어난다. 이를 '동기식(Synchronous) API 호출'로 처리할 때의 문제점과 비교하여, '메시지 큐 기반의 비동기 이벤트 처리' 구조로 변환했을 때 수신 시스템 장애 상황에서 얻을 수 있는 시스템 안정성 효과를 설명하시오.

 - 동기식 호출의 문제점 : 송신 시스템이 모든 하위 시스템의 처리가 완료될 때까지 대기해야 하므로 사용자 응답속도가 현저히 느려진다.
후속 시스템 중 하나라도 장애가 발생하면 전체 주문 트랜잭션이 실패하는 연쇄 장애가 발생한다.

 - 메시지 큐 기반의 비동기 이벤트 처리 구조로 변환했을 때의 효과
	- 주문 시스템은 주문 이벤트를 발생한 후 즉시 응답을 완료할 수 있어 시스템 간 결합도가 낮아진다.
	- 배송/SMS 시스템에 장애가 발생하더라도 발행된 메시지는 메시지 큐에 안전하게 대기상태로 보관된다. 수신 시스템이 복구된 이후 큐에서 메시지를 순차적으로 꺼내어 처리할 수 있으므로, 데이터 손실이나 서비스 전체 중단 없이 시스템의 가용성과 높은 결함 허용성을 확보할 수 있다.
