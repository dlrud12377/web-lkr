## 실무 시나리오

A 온라인 쇼핑몰은 회원과 주문 데이터를 관리하는 시스템을 운영하고 있다.

현재 개발팀은 주문 조회 성능 저하 문제를 해결하기 위해 물리 데이터 모델을 개선하려고 한다.

다음과 같은 요구사항이 존재한다.

- 회원은 여러 개의 주문을 생성할 수 있다.
- 존재하지 않는 회원의 주문 데이터는 저장되면 안 된다.
- 회원 이메일은 중복되면 안 된다.
- 회원 이름은 반드시 입력해야 한다.
- 특정 회원의 주문 내역 조회가 자주 발생한다.
- 다음 조회가 하루 수천 번 이상 실행된다.

# 문제

위 요구사항을 만족하도록 물리 데이터 모델을 설계하려고 한다.

다음 조건에 맞게 SQL을 작성하시오.

# 조건

- DBMS는 MySQL을 사용한다.
- PK 컬럼명은 테이블명_id 형식을 사용한다.
- 회원 테이블명은 `members` 이다.
- 주문 테이블명은 `orders` 이다.
- 회원 테이블 컬럼은 다음과 같다.

| 컬럼명 | 데이터 타입 |
| --- | --- |
| member_id | INT |
| member_name | VARCHAR(50) |
| email | VARCHAR(100) |
- 주문 테이블 컬럼은 다음과 같다.

| 컬럼명 | 데이터 타입 |
| --- | --- |
| order_id | INT |
| member_id | INT |
| order_date | DATE |
- 회원 테이블에는 PK, UNIQUE, NOT NULL 제약조건을 반드시 적용한다.
- 주문 테이블에는 FK 제약조건을 반드시 적용한다.
- 회원 번호 조회 성능 향상을 위한 단일 인덱스를 생성한다.
- 회원번호 + 주문일 조건 검색 성능 향상을 위한 복합 인덱스를 생성한다.
- FK 이름은 `fk_orders_members` 로 작성한다.
- 단일 인덱스 이름은 `idx_orders_member_id` 로 작성한다.
- 복합 인덱스 이름은 `idx_orders_member_date` 로 작성한다.

# 작성해야 하는 내용

1. `members` 테이블 생성 SQL
2. `orders` 테이블 생성 SQL
3. 단일 인덱스 생성 SQL
4. 복합 인덱스 생성 SQL

- 월별 예약 조회 속도가 느리다.
- 오래된 예약 데이터 삭제 작업 시간이 오래 걸린다.
- 백업 시간이 계속 증가하고 있다.

개발팀은 예약일 기준으로 데이터를 분리하여 관리하려고 한다.

# 문제

위 상황에서 가장 적절한 물리 데이터 모델 설계 방식을 작성하고, 그 이유를 서술하시오.

# 작성해야 하는 내용

1. 적용해야 하는 설계 방식
 - 파티션 설계(조합 분할)
2. 적용 이유
 - 예약일 기준으로 데이터를 분리하고 싶고, 그것의 기준이 예약일이므로
 - 데이터량이 많은 곳을 서브파티션으로 분할하고, 전체적으로는 예약년도 등의 기준으로 분할을 하면
