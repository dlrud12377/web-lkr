화면 설계

1. 요구사항 확인하기

1-1. 요구사항 확인
 - UI, UX의 개념 : UI는 화면의 구성요소들, UX는 화면을 포함한 사용자 경험
 - UI/UX의 요소
	UI - 시각적 디자인, 상호작용 디자인, 정보구조
	UX - 사용성, 유용성, 매력도, 접근성, 신뢰성
 - UI/UX의 관계 : 좋은 UX는 UI를 필요로 함. BUT 좋은 UI가 꼭 좋은 UX를 보장해주지는 않음
 - UI/UX의 표준(ISO 9241-210) : 사용자 설정 UI 표준 - 사용자 중심 설계 6대 원칙을 담고 있음

수행하기 / UI 요구사항 확인하기
 - 소프트웨어 개발을 위한 사용자 화면 표준 및 지침 확인(ISO 9241-210, WCAG 2.2, IEEE 830...)
	ㄴ 국내 지침, 국제 표준, 플랫폼별 고려사항 확인, 실현가능성
 - 목표 응용소프트웨어의 UI 요구사항을 확인한다(위의 상황들 중 어떤 것에 해당하는지)
	ㄴ 사용자 면담 및 UI/UX 요구사항 수집 / 토대로 사용자 페르소나 분석
		ㄴ 면담 - 설문 일정, 설문 유형(객관/주관/복합형), 방식(온라인/오프라인) 고려
		ㄴ 내용의 적절성(어려운 질문인지, 중복된 질문인지, 누락된 질문인지, 질문의 방향성이 치우쳐져있지는 않은지)
	ㄴ UI 구성 요소 / 기능 확인 / 흐름 파악 (버튼 입력, 체크박스 등등)
		-> UI 요구사항 도출 및 정리 -> UI 요구사항 명세서를 작성

※ 명세서 작성 시 표준이 있는 건 아님
ID, 요구사항 설명, 유형(기능/비기능), 우선순위, 난이도, 중요도
	-> 회사에서 UI 요구사항을 검토/피드백하고 수정 후 확정(수정 시 버전 기록)
	-> 피드백 수정을 거치면서 버전을 기록한다.


1-2. 프로토타입 제작 및 검토
 - 프로토타입의 개념 : 본격적인 프로그램 제작 진행 전 프로그램이 요구사항에 부합하는지 확인하기 위해 화면 구현 정도만 진행한 프로그램 모델
 - 프로토타입의 유형
	- 초기 프로토타입(low-fidelity prototype) : 화면의 구성 요소 정도만 구현을 해둔 프로토타입
	- 모사형 프로토타입(high-fidelity prototype) : 실제 완성 화면과 거의 비슷하게 구현을 해둔 프로토타입
 - 프로토타입의 제작 절차
 - 프로토타입 설계 및 제작 도구
	ㄴ 초기 프로토타입 설계 도구
		- Adobe XD(개발중단), Sketch(MacOS, Symbol 디자인), Balsamiq(드래그 앤 드롭, 빠른 화면 설계 / 협업지원)
	ㄴ 모사형 프로토타입 설계 도구
		- Figma(무료, 무설치, 협업가능), UXPin(개발환경과 유사 / 실제 구현 검증), ProtoPie(노코딩, 인터렉션(사용자의 반응에 따라 움직임) 제공, 멀티모달), Axure RP(복잡한 업무시스템 구현, 실제 서비스 수준의 테스트)

수행 내용 / UI 프로토타입 제작, 검토하기
 - UI 요구사항을 바탕으로 구성 요소를 정의하고 흐름을 설계하여 프로토타입 제작
	ㄴ UI 구성 요소 정의
	ㄴ UI 흐름 설계
	ㄴ 기능 중심의 UI 설계 초안 작성
	ㄴ 모사형 프로토타입 제작
	 - 제작한 UI 프로토타입의 적정성을 검토한다.
	ㄴ 사전에 정의한 스타일 가이드와 디자인 기준을 준수하였는지 확인
	 - 디자인 기준
	 - 스타일 가이드 : 프로젝트 전체에 적용할 디자인 규칙(EX. 색상, 폰트, 버튼 모양, 간격, 아이콘 스타일...)
	ㄴ 버튼, 입력창 등에 동일한 기능 요소가 일관적으로 적용되었는지 확인
	ㄴ 시각적 요소인 아이콘과 텍스트 정렬 상태, 오타 및 간격 점검
	ㄴ 상호작용 시 상태 표현(활성/비활성/에러 등)의 일관성 확인
 - 화면 흐름 및 연계성을 검토
	 ㄴ 유스케이스(Use Case) 흐름에 따른 화면 전환 및 기능 배치 여부 확인
	 ㄴ 오류 발생 시 경고창이나 안내 메시지가 적절하게 처리되었는지 점검
 - 사용자 테스트 수행
 - 접근성 및 반응성 점검
 - 검토 의견을 취합하여 개선 사항 정리

UI 흐름 설계
1. UI 설계서 구성에 따른 작성 방법
 - UI 설계서 표지
 - UI 설계서 개정 이력(버전 관리)
 - UI 요구사항 정의(UI 메뉴 구조 설계)
 - 사이트맵(UI 구조에 포함되는 메뉴를 사이트맵으로 만들기)
 - 프로세스 정의(사용자가 요구하는 시스템 구동순서에 맞춰 프로세스 정리하기)
 - 화면 설계(필요한 화면 설계)  

2. UI 화면 설계의 기본 구성요소
 ISO 9241-161
 - 사용자와 컴퓨터의 상호작용(HCI, Human Computer Interaction)
 국제 표준
 - 화면 설계 시 자주 사용되는 기본 UI 구성 요소를 정의하고 있다.
 - 그 중 기본 구성 요소를 버튼, 체크박스, 입력창 등 51개 항목으로 제시한다.

 주요 UI 구성 요소
 - 컨테이너 ( 다른 요소들을 포함하는 요소 - 일종의 액자 )
 - 버튼 ( 명령 실행, 제출, 다른 페이지로 이동 - 상호작용이 가능한 요소 )
 - 체크박스 ( 복수 선택 가능한 상호작용 UI 요소 )
 - 라디오버튼 ( 그룹 중 하나만 선택 가능한 상호작용 UI 요소 )
 - 입력창 ( 사용자가 텍스트를 적을 수 있음 )
 - 라벨 ( 제어 요소의 식별자 및 설명을 제공 )
 - 목록 ( 항목 정렬 )
 - 대화상자 ( 사용자 피드백, 확인 요청, 알림 등 )
 - 폼 ( 입력, 선택, 클릭과 같은 전체를 구성하는 복합 요소 )

3. 유용성 개념 및 적용 원리 파악

 3-1. 유용성 : 사용자가 시스템을 활용하여 자신이 원하는 목표를 얼마나 효과적이고 효율적으로 달성할 수 있는지를 의미한다.

 유용성이 높은 시스템
 - 로그인 버튼을 쉽게 찾을 수 있다.
 - 원하는 메뉴를 바로 찾을 수 있다.
 - 검색 결과가 빠르게 나온다.

 유용성이 낮은 시스템
 - 메뉴 위치를 찾기 어렵다.
 - 버튼 이름이 이해되지 않는다.
 - 기능을 사용하기 위해 너무 많은 단계를 거쳐야 한다.

 * 유용한 시스템을 설계할 때 고려사항
 - 시스템을 설계할 때 사용자가 생각하는 방식과 실제 시스템이 동작하는 방식의 차이를 줄여야 한다.

 회원가입 -> 약관 설명 화면 -> 광고 화면 -> 회원가입 화면 방식으로 작동하면 사용자는 불편함을 느낀다.
 
 즉 사용자가 예상하는 동작과 실제 동작이 다르면
	1. 혼란 발생
	2. 사용시간 증가
	3. 서비스 만족도 감소
 가 발생한다.

 * 사용자 모형과 개발자 모형간의 차이 발생
 
 사용자 모형(User Model)
  : 사용자가 머릿속으로 생각하는 시스템의 모습

 개발자 모형(Developer Model)
  : 개발자가 시스템을 구현한 방식

 -> 시스템에서 제공하는 실행 가능한 기능과 사용자가 본래 기대한 목적이 서로 다를 때 발생

 3-2. 실행 차를 최소화하기 위한 UI 설걔 원리
 ※ 실행 차 : 사용자가 원하는 행동과 실제 시스템 조작 사이의 차이(사용자 모형과 개발자 모형의 차이)

 * 사용 의도 파악
 - 사용자가 무엇을 이루려고 하는지 명확하게 이해
 - 불필요한 부가 기능으로 인해 시스템 성능이 저하되지 않도록 설계
 - 사용자가 관심을 가질 만한 항목은 눈에 잘 띄는 곳에 두기
 - 필요한 순간에 기능이 제공되도록 배치

 * 행위 순서 규정
 - 사용자의 행동 과정을 세분화하여 순서대로 명확하게 안내하되, 필요할 경우 사용자가 의도에 맞게 순서를 자유롭게 바꿀 수 있다.
 - 한 가지 작업을 완료하는 단계는 가능한 최소화 하기
 - 동일한 결과를 다양한 방식으로 얻을 수 있도록 설계에 반영하기
 - 행위 순서는 사용자의 기존 경험과 자연스럽게 이어지도록 친숙하게 구성하기

 * 행위의 순서대로 실행
 - 사용자가 계획한 작업 절차를 UI 상에서 직관적으로 파악할 수 있도록 제공하여 의도한 행위를 실제로 실행하는 과정에서 혼란이나 어려움이 생기지 않도록 해야한다.
 - 불필요하게 많은 상호작용으로 인해 작업 진행이 방해받지 않도록 주의해야 한다.
 - 사용자가 의도한 행위에 가장 적합한 입력 장치를 선택하고, 이에 대한 적절한 피드백과 취소 기능을 제공한다.
 - 기본값을 알맞게 설정해 불필요한 조작을 줄여야 한다.

 3-3. 평가 차를 줄이기 위한 UI 설계 원칙
  ※ 평가 차 : 사용자가 시스템의 상태를 이해하는 과정에서 발생하는 차이

 * 키 입력 결과를 사용자가 신속하게 인식할 수 있도록 설계
 - 사용자가 어떤 조작을 했음에도 화면에 아무런 변화가 없다면
	-> 사용자가 제대로 입력했는지 의심
	-> 평가 차를 키우게 된다.
 	-> 따라서, 가능한 빠르게 시스템이 반응하도록 설계 OR 즉각적인 반응이 어렵더라도 지연을 최소화해야 한다.
 - 또한 사용자가 행위를 했다는 사실이 명확히 드러나도록 직관적인 피드백을 제공해야 한다.

 * UI 조작으로 인해 시스템의 상태 변화를 쉽게 파악할 수 있도록 설계
 - 사용자의 입력에 따라 시스템이 어떻게 달라졌는지 명확하게 인식할 수 있어야 한다.
 - 이를 위해 상태 정보를 단순하고, 이해하기 쉽게 표현해야 하며, 복잡하지 않도록 설계하는 것이 좋다.

 * 사용자의 의도와 시스템 반응 결과의 일치 여부를 쉽게 확인할 수 있도록 설계
 - 사용자가 기대한 결과가 실제 시스템을 통해 충족되었는지 쉽게 알 수 있어야 한다.
 - 이를 위해 미리보기와 같은 기능을 제공하면 사용자가 예상 결과를 사전에 확인할 수 있어 대부분의 경우 만족도를 높일 수 있다.

 4. 스토리보드 작성 방법
 - 스토리보드 : 서비스 구축 과정에서 디자이너와 개발자가 공통으로 참고하는 최종 산출물
 -> 정책, 프로세스, 콘텐츠 구성, 와이어프레임, 기능 정의, 데이터베이스 연동 등 서비스 구현에 필요한 핵심 정보가 들어가 있다.'
 
 4-1. 메뉴 구성도 작성
 - 전체 서비스의 메뉴 구조를 정의
 - 사용자가 어떤 경로로 서비스를 이용하는지 파악
 - 화면 간 이동 관계를 명확하게 정리

 4-2. 스타일 확정
 - 서비스 전체의 디자인 일관성 유지하기
 - 화면마다 다른 디자인이 적용되지 않도록 기준 설정하기
 고려대상 : 색상(주, 보조, 배경, 글씨색), 글꼴, 버튼 & 입력창 스타일, 아이콘 및 그래픽

 4-3. 설계
 - 실제 화면에 표현될 시각적 디자인 콘셉트를 구체화 한다.

 * 수행 내용 / UI 흐름 설계하기
 1. 유용성을 적용한 UI 설계안의 적정성 확인하기

 1-1. 실행 차를 줄이기 위한 UI 설계 원리를 확인한다.

   - 사용 의도를 정확히 파악한다.
	- 불필요한 부가 기능이 있는지 확인
	- 중복되는 기능이 있는지 확인

   - 행위 순서를 규정한다.
	- 어떤 사전 행위들이 수행되어야 하는지 나열
	- UI 설계서를 이용해 기능의 중요도 나누기
	- 중요도 상 등급의 기능 수행 단계 수가 최소화되어있는지 확인
	- 전체적인 기능 사용 단계 수가 적절한지 확인

   - 기능 수행 절차에 따른 실행 순서 정의
	- 화면 설계서에 편집 창 포함 시 커서와 포인터 중 어떤 요소가 먼저 활성화되어야 하는지
	- 편집 창이 여러 개인 경우, 사전 행위 기반 올바른 커서의 시작 위치 지정
	- 메뉴 활용 시 초기 상태에서 어떤 값이 우선적으로 활성화될지 정의
	- 이 외에도 Default Value가 필요한 요소가 있는지 확인

 1-2. 평가 차를 줄이기 위한 UI 설계 원리 확인

   - 수행한 키 조작의 결과를 사용자가 빠르게 자각 가능한지 확인
	ㄴ 즉각적인 피드백 제공이 필요
	- UI 설계서의 각 화면 설걔 결과에서 메뉴/아이콘/윈도우 활성화 시 적절한 포인터의 형태 결정
	- UI 설걔서의 각 화면 설계 결과에서 각 기능이 수행되는 동안 적절한 포인터의 형태 결정

   - 키 조작으로 변화된 시스템의 상태를 사용자가 쉽게 인지 가능한지 확인
	ㄴ EX. 에러 코드를 띄워주지 말고, 어떤 에러가 나서 어떠한 해결방안이 필요한지 결과를 직관적으로 알려주어야 함

   - 사용자가 가진 원래 의도와 시스템 결과 간의 유사 정도를 사용자가 쉽게 파악 가능한지 확인

 2. UI 요구사항과 UI 표준 및 지침에 따라, 화면과 폼의 흐름을 설계한다.

 2-1. 화면에 표현되어야 할 기능을 작성한다.
   - 목표 시스템의 기능 요구사항을 분석 및 검토
	- 목표 시스템에서 개별 기능 요구사항이 무엇인지 정의
		ㄴ 입력 항목, 출력 항목, 데이터, 연산, 기타 요구사항 분석
	- 구축 예정 시스템에서 각각의 기능적 요구사항의 설명 정리
		ㄴ CUD 정리, 이벤트 발생 시 필요 기능 숙지, 검색 용이성 조사, 입출력기능 검토, 특정 시스템 기능 조사, 기타 사용자 편의성을 높이는 기능에 대해 조사

   - 목표 시스템의 비기능 요구사항을 분석 및 검토
	- 목표 시스템에서 비기능 요구사항이 무엇인지 정의(시스템 품질, 환경, 프로젝트 관리 관련 요구사항 조사)
	- 목표 시스템의 비기능 요구사항에 대한 설명을 정리(운영체제 종속성이 없는지, 시스템 부분 오류로 인한 전체 작동 정지 여부, DB의 안정성, 이벤트 처리 속도는 요구사항을 만족하는지, 설정해 둔 제약사항이 잘 지켜지는지)

 2-2. 화면의 입력 요소를 확인한다.
 - 화면에 표현되어야 할 기능을 확인한다.
	ㄴ EX. 도서 대출 예약 시스템 화면 표현 기능 확인 사례
	 -> 사용자가 자신의 계정인 아이디와 패스워드를 입력할 수 있어야 한다.
	 -> 시스템이 도서 탐색 화면을 제공해 주어야 한다.
	 -> 시스템이 색인 정보를 제공해 주어야 한다.
	 -> 사용자가 책 이름을 입력할 수 있어야 한다.
	 -> 시스템은 일치하는 책을 검사하여 사용자가 선택 가능한 리스트 제공
	 -> 사용자가 책을 선택할 수 있어야 한다.
	 -> 시스템이 예약 여부를 제공해 줄 수 있어야 한다.
	 -> 예약이 이루어진 경우 예약 내역 또는 대출 내역이 색인에 반영되어야 한다.

 2-5. 기능 및 양식을 확인한다.
 - 입력창(Input)을 확인하고, 규칙을 정의한다.
	ㄴ 입력 가능 여부를 구분하여 CSS(스타일)를 적용한다.
	ㄴ 필드의 길이는 자료의 길이와 일치하게 만든다.
	ㄴ 텍스트 정렬 방식은 가운데 정렬한다.
	ㄴ 라벨은 좌측 정렬한다.
	ㄴ 필수 입력 항목을 구분해 Label에 다음과 같이 CSS를 적용한다.
	일반 입력 Label: HTML <th></th>
	필수 입력 Label: Label Text 뒤에 * 표시를 넣는다.

 - Combo Box를 확인하고, 규칙을 정의한다.
	ㄴ 선택 항목이면서 Default값이 없을 경우 '전체' 혹은 '선택'의 기본 문구로 통일한다.
	ㄴ 콤보 박스 버튼의 초기 설정값은 자주 사용하는 값을 우선한다.
	ㄴ 콤보 박스 버튼을 클릭하면 별도의 저장 버튼을 눌러서 저장이 되도록 한다.

 - 라디오 버튼을 확인하고, 규칙을 정의한다.
	ㄴ 라디오 버튼을 사용할 경우 텍스트와의 정렬이 맞도록 CSS를 적용한다.
	ㄴ 라디오 버튼의 초기 설정값은 자주 사용하는 값으로 우선한다.
	ㄴ 라디오 버튼을 클릭하면 자동으로 선택된 값이 저장되도록 한다.

 - 체크박스를 확인하고, 규칙을 정의한다.
	ㄴ 체크 박스 버튼을 사용할 경우 텍스트와의 정렬이 맞도록 CSS를 적용한다.
	ㄴ 체크 박스 버튼의 초기 설정값은 자주 사용하는 값을 우선으로 한다.
	ㄴ 체크 박스 버튼을 클릭하면 별도의 저장 버튼을 눌러서 저장이 되도록 한다.
