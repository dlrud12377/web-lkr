어플리케이션 테스트 수행하기

< 테스트와 소프트웨어 개발 생명주기 >
소프트웨어 아키텍트와 테스트 매니저가 V(↘개발 ↗테스트) 모델 상에서 서로 보완 관계를 형성한다.

좌 -> 우
↘(개발 순서) : 요구사항 분석, 아키텍쳐 설계, 모듈 설계, 구현
↗(테스트 진행 순서) : 단위테스트, 통합 테스트, 시스템 테스트, 인수 테스트
(1234 - 4321 순)

테스트는 개발 완료 후 시작되는 것이 아니라 각 개발 단계 산출물과 1:1로 대응
요구사항 분석 ↔ 인수 테스트 : 사용자 요구사항 만족 여부 검증
아키텍쳐 설계 ↔ 시스템 테스트 : 전체 시스템의 정상 작동 검증
모듈 설계 ↔ 통합 테스트 : 모듈 간 연결 정상 작동 검증
구현 ↔ 단위 테스트 : 개발 코드 및 모듈 정상 작동 검증

1. 단위 테스트(Unit Test)
 - 모듈, 컴포넌트 단위의 최소 기능 검증

모듈(Module) : 프로그램에서 특정 기능을 담당하도록 묶어놓은 코드 단위
	ㄴ 로그인 기능(요청 -> controller -> service -> dao -> db -> dao -> service -> controller)
컴포넌트(Component) : 프로그램을 구성하는 독립적인 기능 단위
	ㄴ 회원 컴포넌트(로그인, 회원가입, 정보수정)

테스트 대상 : 하나의 메서드, 클래스, 서비스, 계산 로직, 데이터 변환 기능 등...

접근 방법
 - 구조 기반 테스트(화이트박스 테스트) : 프로그램 내부 구조의 제어 흐름, 조건 결정, 예외 처리 경로 등을 코드를 알고 있는 상태에서 검증
 - 명세 기반 테스트(블랙박스 테스트) : 내부 코드 대신 요구사항과 입출력 결과에 집중하며 동등 분할과 경곗값 분석 기법을 활용한다.

2. 통합 테스트(Integration Test)
 - 모듈 간 인터페이스 및 상호작용을 검증
 - 개별 모듈이 정상이어도 연결 과정에서 발생하는 오류를 잡아낸다

3. 시스템 테스트(System Test)
 - 통합된 전체 시스템이 요구사항을 완전히 수행하는지 실제 운영환경과 유사한 조건에서 검증

4. 인수 테스트(Acceptance Test)
 - 최종 사용자 및 업무 이해관계자가 실제 업무 운영 여부를 결정하기 위해 수행한다.
 - 단순 오류 실행 유무가 아닌 실제 업무 적용 가능성을 검증한다.


< 통합 테스트의 종류 >

1. 빅뱅 테스트 : 모든 모듈을 한꺼번에 결합하여 테스트
 - 장점 : 세밀한 계획 불필요, 모듈 수 적을 때 신속함
 - 단점 : 오류 원인 추적이 어려움, 모든 모듈 개발 전까지 시작 불가

2. 상향식(Bottom Up 방식) : 하위 모듈(DAO)부터 상위 모듈(Controller) 순으로 결합
 - 드라이버(Driver) : 미개발된 상위 모듈을 대신해 하위 모듈을 시행시키는 가짜 상위 모듈
	 - 장점 : 하위 모듈만 빠르게 검증할 수 있다.
	 - 단점 : Driver를 별도로 작성해야 한다.

3. 하향식(Top Down 방식) : 상위 모듈(Controller)부터 하위 모듈(DAO)로 결합
 - 스텁(Stub) : 미개발된 하위 모듈 대신 미리 준비된 가짜 결과를 반환하는 임시 모듈
 - 장점 : 화면/업무 로직을 빠르게 검증할 수 있다.
 - 단점 : Stub의 별도 작성이 필요하다.

4. 샌드위치 : 상향식과 하향식을 동시에 진행하여 중간 계층에서 연결
 - Driver와 Stub을 모두 사용한다
 - 테스트 기간 단축 및 병렬 진행 가능

5. 중앙식 : 중앙 통제 모듈(Hub)을 중심으로 모듈 간 데이터 전달 및 제어 수행

6. 협업식 : 모듈 간 직접 연계하여 실제 운영 환경과 유사하게 연계성 검증

7. 레이어 통합 : 계층 단위로 결합하여 인접 계층 및 전체 구조 검증

< 시스템 테스트의 종류 >

1. 기능 요구사항 테스트 : 시스템이 수행해야 할 기능에 대한 명세 기반 블랙박스 테스트
ex.
 - 회원가입을 할 수 있어야 한다.
 - 상품을 조회할 수 있어야 한다.
 - 주문을 취소할 수 있어야 한다. 

2. 비기능 요구사항 테스트 : 성능, 회복, 보안, 네비게이션 구조 등 화이트박스 및 비기능 요소 검증
ex.
 - 조회 결과는 3초 이내에 표시되어야 한다.
 - 동시에 1,000명이 접속할 수 있어야 한다.
 - 사용자 비밀번호는 암호화되어야 한다.
 - 서버 장애 후 10분 이내에 복구되어야 한다.

< 인수 테스트 >
 - 개발이 완료된 시스템의 최종 사용 운영 가능 여부를 결정하는 6가지 테스트(선택이 아니라 모두 해야 함)

1. 사용자 인수 테스트 : 비즈니스 사용자가 업무 사용의 적절성을 확인

2. 운영상의 인수 테스트 : 시스템 관리자가 백업/복원, 재난 복구, 정기 점검 등 확인

3. 계약 인수 테스트 : 계약상의 인수 및 검수 조건 준수 확인

4. 규정 인수 테스트 : 정부 지침, 법률, 규정, 표준 등의 준수 여부를 확인

5. 알파 테스트 : 개발 조직 내부의 잠재 고객이 수행

6. 베타 테스트 : 실제 환경에서 외부 사용자가 수행

< 테스트 기반에 따른 테스트의 종류 >

1. 구조 기반 테스트
 - 소프트웨어 내부 구조, 소스 코드, 제어 흐름, 조건식을 기준으로 테스트 케이스를 설계하는 화이트 박스 테스트 기법
 - 단순히 어떤 입력에 어떤 결과가 나오는지만 확인하는 것을 넘어, 코드 내부의 제어 흐름과 구문들이 실제로 실행되는지를 검증한다.
 - 검증 세부사항
	 - 각 명령문이 실행되었는지
	 - if문의 참 거짓 경로가 모두 실행되었는지
	 - 복합 조건식의 개별 조건이 참과 거짓을 모두 가졌는지
	 - 반복문의 내부와 종료 경로가 실행되었는지
	 - 실행 가능한 주요 경로가 충분히 테스트 되었는지

 * 구조 기반 테스트의 세부 커버리지 유형
 - 커버리지 : 테스트가 프로그램을 얼마나 빠짐없이 확인했는지를 수치적으로 표현한 척도
	(1). 구문 커버리지 : 프로그램 내부의 모든 문장을 최소 한 번 이상 실행하도록 테스트 케이스 구성
	(2). 조건 커버리지 : 조건식 안에 포함된 개별 조건이 참과 거짓을 적어도 한 번씩 갖도록 테스트 케이스를 작성
	(3). 결정 커버리지 : 전체 조건식의 결과가 참과 거짓이 되는 상황을 각각 최소 한 번 이상 실행한다.
	(4). 조건/결정 커버리지 : 개별 조건식도 참/거짓을 모두 만족하고, 전체 조건식도 참/거짓을 모두 만족하도록 결합한 기법
		(조건 커버리지와 결정 커버리지가 모두 100%가 되도록 테스트 케이스를 구성)
	(5). 변경 조건/결정 커버리지 : 다른 개별 조건의 결과에 영향을 받지 않고, 해당 개별 조건 단 하나에 의해 전체 결정 결과가 달라지는 경로를 검증한다.(조건/결정 커버리지 100% + 전체 결정이 어떤 조건에 의해 어떻게 바뀌는지까지 파악한 테스트 케이스를 구성)
	(6). 다중 조건(Multi-Condition Based : 멀티 조건 기반) 커버리지 : 조건식 내 개별 조건들의 가능한 모든 논리적 조합을 전부 테스트한다.
2. 명세 기반 테스트
 - 소스코드를 보지 않고, 요구사항 명세서, 설계서, 비즈니스 규칙 등 소프트웨어 명세를 바탕으로 입출력 결과를 검증하는 블랙박스 테스트 기법
 - 개발자 시점이 아닌 사용자 및 기획자 시점에서 시스템이 요구된 대로 동작하는지 검증한다.

	테스트 기법 종류
	(1). 동등 분할
	 - 입력값 영역을 유효한 값과 유효하지 않은 값의 균등한 그룹으로 나누고, 각 그룹에서 대표값 하나씩을 선정하여 테스트한다.
	 - 최소한의 테스트 케이스로 전체 입력 영역을 효율적으로 커버한다.

	(2). 경곗값 분석
	 - 오류가 발생하기 가장 쉬운 경계 부근의 값(경계값, 경계 바로 위/아래 값)을 집중적으로 테스트한다.
	 - 14세 이상 -> 13, 14, 15세를 테스트

	(3). 결정 테이블 테스트
	 - 복잡한 조건 조합과 그에 따른 행동을 표 형태로 정리하여 모든 비즈니스 규칙 조합을 검증한다.
	 - 조건의 개수가 n개라면 테스트 케이스는 2^n개

	(4). 상태 전이 테스트
	 - 시스템의 상태 변화와 이벤트에 따른 상태 이행 과정을 검증한다.

	(5). 유스케이스 테스트
	 - 실제 사용자의 이용 시나리오 흐름에 따라 기본 흐름과 대안 흐름, 예외 흐름을 테스트한다.

3. 경험 기반 테스트
 - 명세서나 코드 구조에 의존하지 않고 테스터의 지식, 경험, 직관, 과거 결함 이력을 바탕으로 수행하는 테스트 기법

	테스트 기법 종류
	(1). 탐색적 테스트
	 - 테스트 케이스를 미리 작성하지 않고, 테스트 수행 과정에서 얻은 시스템 이해를 바탕으로 테스트 설계와 실행을 동시에 진행한다.

	(2). 리스크 기반 테스팅
	 - 모든 기능을 동일한 비중으로 테스트하지 않고, 문제가 발생할 가능성이 높거나 문제가 발생했을 때 피해가 큰 기능을 우선적으로 테스트하는 방법

< 테스트 자동화 >
 - 소프트웨어 테스트는 시간과 비용이 많이 든다
 - 테스트의 정확성을 유지하려면 시간과 비용을 줄일 수 있는 자동화 도구가 중요해졌다.
 - 같은 기능을 여러번 반복해서 테스트해야 하는 경우 사람이 직접 수행하면 많은 시간이 필요하다.
 - 프로그램이 수정될 때마다 이를 다시 수행해야 하므로 자동화 도구를 사용하면 반복 작업을 줄일 수 있다.

??

	< 테스트 자동화의 흐름 >
	1. 테스트 조건 정의
	2. 자동화 스크립트 작성
	3. 테스트 실행
	4. 실제 결과 수집
	5. 예상 결과와 비교
	6. 결과 보고서 생성

	< 자동화가 적합한 테스트의 조건 >
	 - 반복적으로 수행하는 테스트
	 - 회귀 테스트
	 - 많은 데이터를 사용하는 테스트
	 - 성능 테스트
	 - API 테스트
	 - 여러 환경에서 반복되는 테스트

	< 테스트 자동화 도구의 장점 >
	 - 테스트 데이터 재입력 및 재구성과 같은 반복작업을 자동화하여 인력과 시간을 줄인다.
	 - 요구사항 정의, 성능 및 스트레스 테스트, 품질 측정을 최적화한다.
	 - 빌드 확인, 회귀 테스트, 다중 플랫폼 호환성, 소프트웨어 구성 및 기본 테스트 등의 품질을 향상한다.
		 - 반복 작업 감소
		 - 결과 일관성
		 - 빠른 피드백
		 - 대량 테스트
		 - 회귀 테스트
		 - 결과 기록

	< 테스트 자동화 도구의 단점 >
	 - 도구 전문가를 양성하거나 고용해야 한다.
	 - 초기 프로세스 적용에 시간, 비용, 노력이 추가로 필요하다.
	 - 비공개 상용 도구는 가격이 높을 수 있다.
	 - 인력과 교육에 대한 유지관리 비용이 발생한다.
	 - 자동화 도구를 도입한다고 즉시 테스트 비용이 줄어드는 것은 아니다.
	 - 화면 구조가 자주 변경되면 자동화 스크립트도 계속 수정해야 하므로 오히려 유지보수 비용이 증가할 수 있다.

	< 테스트 자동화 도구 평가 방법 및 요소 >
	
	1. 평가 방법
	 - 테스트 도구가 지원하는 기능을 종류별로 나열하고 기록한다.
	 - 테스트 요소의 목표값이나 평균값을 설정한 후 해당 기준에 따라 평가한다.
	 - 비용을 줄이기 위해 일부 필수 요소만 고려해야 한다면 최소한의 오규사항을 만족하는 도구를 선정한다.

	2. 평가 요소
	 - 사용 편의성
	 - 다중 사용자 접속
	 - 결함 추적
	 - 도구 기능성
	 - 보고 능력
	 - 성능 및 스트레스 테스트
	 - 버전 제어

< 어플리케이션 테스트 수행하기 >

	1. 테스트 계획서를 확인한다
	 - 기존에 작성된 테스트 기획서를 활용하여 사용자 요구사항을 일관성 있게 계획, 설계, 실행할 수 있도록 전체 테스트 순서와 방법을 확인한다.

		(1). 테스트 목적을 확인한다.
		 - 테스트 목적 : 정보시스템 개발 중 다음 사항을 검증하여 시스템 품질을 확보하는 데 있다.
			 - 프로그램 기능의 정확성
			 - 프로그램 기능의 완전성
			 - 예외 상황 처리의 적절성
			 - UI 표준 준수 여부
			 - 개발 표준 준수 여부

		 - 테스트 범위
			 - 성능 테스트 기간과 진행 자원에 따라 달라질 수 있다.
			 - 테스트 범위를 정하지 않으면 제한된 일정 안에 모든 기능을 확인하려다가 중요한 기능을 충분히 테스트하지 못할 수 있다.

		 - 범위 선정 기준
			 - 업무 중요도가 높은 기능
			 - 장애 발생 시 영향이 큰 기능
			 - 최근 변경된 기능
			 - 외부 시스템과 연계된 기능
			 - 데이터 처리량이 많은 기능
			 - 사용 빈도가 높은 기능

		(2). 테스트 실행 계획을 확인한다

			 - 테스트 시작 기준과 종료 기준을 확인한다.
				 - 시작 기준 : 개발 진척률이 50% 이상일 때 단위 테스트를 시작한다.
				 - 종료 기준 : 오류가 얼마나 남았는지 완벽하게 알 수 없으므로 테스트를 종료할 기준을 미리 정한다.		
					ㄴ 모든 단위 시험 케이스가 성공적으로 기록된 경우
					ㄴ 일부 케이스가 통과하지 않았지만 영향이 제한적이라고 판단되는 경우
					ㄴ 중대한 결함이 만족스럽게 조치되고 재테스트에서 해결된 것으로 판단되는 경우
					ㄴ 수정되지 않은 결함이 존재하더라도 전체 검토 결과 영향이 제한적이라고 확인된 경우
				 - 테스트를 종료한다는 것은 결함이 하나도 없다는 의미가 아니다. 치명적인 결함이 없는 정도면 테스트를 종료할 수 있다.

			 -  테스트 수행 절차를 확인한다.
				 - 각 담당자의 역할과 보고 체계를 확인한다.
					 - 테스트 관리자 : 테스트 계획 수립, 결과 검토 및 분석
					 - 업무별 팀장 : 테스트 계획 검토, 테스트 수행 관리, 결과 확인
					 - 개발자 : 테스트 케이스 작성, 테스트 수행, 결함 수정
					 - 기술 지원 : 테스트 방법 교육, 환경과 도구 지원

		(3). 테스트 케이스를 확인한다.
		 - 테스트 케이스로 선정된 주요 업무는 테스트 시나리오에 따른 세부적인 업무 처리 절차를 정의한다.
		 
			 - 테스트 시나리오를 확인한다.
				로그인
				→ 상품 선택
				→ 상품 구매
				→ 주문서 작성
				→ 결제
				→ 주문 완료

			 - 테스트 케이스를 확인한다.
				 - 해당 내용 표 확인


		(4). 테스트 데이터를 확인한다.
		 - 특정 데이터를 사용하여 연속된 업무를 처리하면 테스트 중 데이터가 생성, 수정, 삭제될 수 있다.
		 - 실제 운영 데이터를 사용할 경우 문제가 발생할 수 있다.
			ㄴ 실제 고객 데이터 변경 또는 삭제
			ㄴ 개인정보 노출
			ㄴ 테스트 주문이 실제 매출에 반영됨
			ㄴ 테스트 메시지가 실제 고객에게 발송됨
			ㄴ 데이터 복구가 어려움

		(5). 테스트 환경을 확인한다.
		 - 테스트 환경에는 다음과 같은 테스트 관련 IT 자원과 도구를 명시한다.
			 - 테스트 대상 장비
			 - 테스트 도구
			 - 테스트용 데이터
			 - 네트워크 환경


		 - 테스트 대상 장비와 주요 사항(테스트 관련 IT 자원과 도구)을 확인한다.
			ㄴ 테스트 결과는 서버 사양에 영향을 받을 수 있기 때문이다.

		 - 테스트에 사용할 도구를 확인한다.
			ㄴ 테스트 생성 도구
				ㄴ 명세 기반 도구
				ㄴ 코드 기반 도구
			ㄴ 테스트 수행 도구
				ㄴ 성능 평가 및 시뮬레이션 도구
				ㄴ 동적 분석 도구
				ㄴ 커버리지 분석 도구
				ㄴ 단순 수행 도구
			ㄴ 테스트 관리 도구
			(자세한 사항은 표 참고)

	2. 기능 단위 테스트를 수행한다.

		(1). 기능 단위를 정의한다.

		 - 서버 모듈
			ㄴ 화면 모듈과 인터페이스에서 전달받은 데이터를 이용하여 업무를 처리한다.
			ㄴ 화면 인터페이스는 화면에서 직접 확인하고 데이터 인터페이스는 DB 정보와 데이터 로그 파일을 통해 확인한다.
			ㄴ 서버 모듈은 사용자의 요청을 받아 실제 업무 규칙을 실행한다.
				ㄴ 재고 확인, 주문 금액 계산, 할인 적용, 결제 요청..	

		 - 화면 모듈
			ㄴ 화면 설계서와 사용자 요구사항에 따라 화면에서 등록, 수정, 삭제, 조회된 내용응ㄹ 확인
			ㄴ 입력항목이 설계서와 일치하는가
			ㄴ 필수 입력값을 검사하는가
			ㄴ 버튼이 정상적으로 동작하는가
			ㄴ 등록, 수정, 삭제 결과가 화면에 반영되는가

		 - 데이터 입출력
			ㄴ 화면 모듈, 인터페이스 및 서버 모듈에서 받은 데이터를 가공하고 저장
			ㄴ 입력값 뿐만 아니라 DB에 실제로 저장된 값과 다시 조회된 결과가 모두 일치해야 한다.

		 - 인터페이스
			ㄴ 인터페이스 : 시스템과 시스템, 모듈과 모듈 사이의 연결부를 의미함
			ㄴ 타 시스템 인터페이스에서 데이터와 엔티티 변환이 정확하게 이루어지는지 확인한다
			ㄴ 요청값 누락, 데이터 형식 불일치, 응답 지연, 인증 결과 오처리, 외부 시스템 연결 실패, 오류 메시지 누락 등의 결함 발생 가능

		(2). 기능 단위 테스트를 통합하여 테스트 항목을 정의한다
		 - 업무별 기능에 따라 각각의 기능 단위가 연결되어 단위 테스트가 이루어지며, 테스트 내용에 따라 테스트 항목이 달라진다.
		(본문 표 확인)

		(3). 단위 테스트를 수행한다.
		 - 테스트 환경 관련 사항을 준비한다
			ㄴ 소스 코드에 직접 접근할 수 있는 권한
			ㄴ 로그 기록 가능 여부
			ㄴ 다중 인스턴스 구성
			ㄴ 로그인 허용 여부
		 - 입출력을 확인한다.
			ㄴ 화면에서 조회, 등록, 수정, 삭제된 내용을 확인하고, DB 쿼리를 이용하여 대상 테이블의 실제 데이터 내용을 확인한다.
		 - 산술식 또는 단숙 계산 결과를 확인한다.
			ㄴ 공학용 계산기나 Excel 등의 응용 프로그램을 사용하여 계산 결과를 비교 확인한다.

		 - 연동 시스템을 확인한다.
			ㄴ 다른 시스템과의 인터페이스에서 데이터와 엔티티가 정확하게 변환되는지 확인한다.

		 - 배치 처리와 인터페이스를 확인한다.
			ㄴ 시스템의 DB 정보와 로그 파일을 통해 처리된 데이터를 확인한다.

		 - 인쇄 및 보고서를 확인한다.
			ㄴ 화면 출력 결과 또는 보고서 도구로 인쇄한 자료에서 다음 항목이 사용자 요구사항과 일치하는지 확인한다.
				 - 데이터 합계
				 - 출력 내용
				 - 보고서 레이아웃

		(4). 통합 테스트를 수행한다
		 - 통합 테스트 환경을 구성한다.
			ㄴ 테스트 대상 장비, 응용 시스템, 데이터, 네트워크 환경을 확인한다

		 - 테스트를 실행하고 결과를 기록한다.
			1. 준비된 환경에서 테스트 시나리오와 케이스에 따라 테스트를 실행한다.
			2. 각 테스트 케이스의 결과와 성공·실패 여부를 기록한다.
			3. 전체 시나리오의 최종 결과를 성공, 실패, 조건부 성공으로 기록한다.
			4. 테스트가 실패하면 결함 관리 절차에 따라 결함을 관리한다.
			5. 결함 조치 후 재수행할 때도 동일한 절차를 따른다.

		 - 통합 테스트 종료 여부를 평가한다

		(5). 성능 테스트를 수행한다
		 - 성능 테스트 계획서를 작성한다
			 - 목표치 설정
				ㄴ 목표 TPS(Transaction Per Second)
				ㄴ 허용 응답 시간
				ㄴ 허용 시스템 사용률
			 - 전체 업무 거래량의 약 80%를 차지하는 업무를 테스트 대상으로 선정
			 - 테스트 대상 업무별 리허설과 시나리오 스크립트 확인
			 - 대기 시간(*Think Time)과 *가상 사용자 수 확인
				ㄴ *Think Time
				 - 사용자가 한 작업을 수행한 후 다음 작업을 수행하기까지 기다리는 시간
				 - ex. 상품 상세 정볼르 5초 동안 읽은 후 구매버튼을 누름 -> Think Time은 5초
				ㄴ *가상 사용자
				 - 성능 테스트 도구가 실제 사용자 대신 생성하는 사용자(프로그램이 서버 환경 재현을 위해 실제 사용자처럼 부하를 일으킴)
			 - 업무별 가중치를 바탕으로 가상 사용자 수 결정
			 - 운영 중인 시스템이라면 피크 시간 부하 분석 후 업무 가중치 산정


		 - 성능 테스트를 수행하고 결과 보고서를 작성한다
		 - 성능 테스트 결과를 분석한다
		 - 성능을 만족하지 못하는 부분이 있다면 병목지점을 찾고 수정한 뒤 테스트를 다시 한다.


< 어플리케이션 결함 관리 >
 - 프로그램과 명세서 간의 차이 또는 업무 내용의 불일치
 - 기대 결과와 실제 관찰 결과 간의 차이
 - 시스템이 사용자가 기대하는 타당한 수준을 충족하지 못해 변경이 필요한 모든 사항
 - 요구사항에 있는 기능이 구현되지 않음
 - 계산 결과가 잘못됨
 - 버튼을 눌러도 반응하지 않음
 - 화면의 용어가 요구사항과 다름
 - 데이터가 DB에 저장되지 않음


< 결함 관리 프로세스 >

	1. 결함 관리 계획
	 - 전체 프로세스에서 결함 관리에 필요한 일정, 인력 및 업무 프로세스를 확보하여 계획을 수립하는 활동이다.
	 - 결함 관리 계획에서는 다음의 사항을 결정한다.
		ㄴ 결함을 어디에 기록할 것인가
		ㄴ 누가 결함을 등록할 것인가
		ㄴ 누가 결함을 검토할 것인가
		ㄴ 누가 수정할 것인가
		ㄴ 심각도와 우선순위를 어떻게 구분할 것인가
		ㄴ 결함 처리 상태를 어떻게 관리할 것인가
		ㄴ 재시험은 누가 수행할 것인가
		ㄴ 결함 보고서를 언제 작성할 것인가

	2. 결함 기록
	 - 테스터는 발견된 결함의 정보를 관리 데이터베이스에 기록한다

	3. 결함 검토
	 - 등록된 결함의 주요 내용을 검토하고, 결함을 수정할 개발자에게 전달한다.
		ㄴ 실제 결함이 맞는가
		ㄴ 요구사항을 잘못 이해한 것은 아닌가
		ㄴ 동일한 결함이 이미 등록되어 있지 않은가
		ㄴ 결함을 재현할 수 있는가
		ㄴ 기록된 정보가 충분한가
		ㄴ 어떤 모듈에서 발생했는가
		ㄴ 심각도와 우선순위가 적절한가
		ㄴ 어느 개발자에게 배정할 것인가
	 - 결함이 아닌 것으로 판정되거나 동일한 결함이 이미 존재하면 수정 대상에서 제외할 수 있다.

	4. 결함 수정
	 - 개발자는 자신에게 할당된 결함이 발생한 프로그램을 수정한다.
		ㄴ 결함의 근본 원인
		ㄴ 수정 대상 코드
		ㄴ 관련된 다른 기능
		ㄴ 수정으로 발생할 수 있는 부작용
		ㄴ DB 또는 설정 파일의 변경 여부
		ㄴ 테스트 케이스 수정 필요 여부
		ㄴ 문서 변경 필요 여부
	 - 단순히 오류 메시지를 없애는 것이 아니라 오류가 발생한 근본 원인을 제거해야 한다.

	5. 결함 재확인
	 - 테스터는 개발자가 수정한 내용을 확인하고 다시 테스트한다.
	 - 결함 재확인은 수정된 기능이 정상적으로 동작하는지를 확인하는 재시험이다.
		ㄴ 재시험 : 발견되었던 결함이 실제로 해결되었는지 확인한다.
		ㄴ 회귀 테스트(Recursion Test) : 수정으로 인해 기존 정상 기능에 새로운 문제가 발생하지 않았는지 확인한다.

	6. 결함 상태 추적 및 모니터링
	 - 결함 관리 팀장은 결함 관리 데이터베이스를 이용하여 대시보드 또는 게시판 형태의 서비스를 제공한다.
	
	대시보드 확인 가능 정보
	- 전체 결함 수
	- 신규 결함 수
	- 수정 완료 결함 수
	- 미해결 결함 수
	- 심각도별 결함 수
	- 담당자별 결함 수
	- 평균 처리 시간
	- 재오픈된 결함 수
	- 테스트 진행률

	7. 최종 결함 분석 및 보고서 작성
	 - 발견된 결함 내용과 이해관계자의 의견을 반영한 보고서를 작성하고 결함 관리를 종료한다.

	최종 결함 보고서 내용
	- 테스트 기간
	- 전체 테스트 케이스 수
	- 성공 및 실패 건수
	- 전체 결함 건수
	- 결함 유형별 통계
	- 심각도별 통계
	- 수정 완료 여부
	- 미해결 결함
	- 주요 결함 원인
	- 재발 방지 대책
	- 시스템 오픈 가능 여부

< 결함의 상태 및 추적 >
 - 결함은 발견된 후 수정하고 종료될 때까지 여러 상태로 변경된다.

	1. 결함 등록(Open)
	 - 테스터 또는 QA 담당자가 결함을 처음 발견하여 등록했지만 아직 분석되지 않은 상태

	2. 결함 검토(Reviewed)
	 - 등록된 결함을 담당 모듈 개발자, 테스터, 프로그램 리더 및 QA 담당자가 검토하는 상태

	3. 결함 할당(Assigned)
	 - 결함의 영향 분석과 수정을 위해 개발자 또는 문제 해결 담당자에게 할당된 상태

	4. 결함 수정(Resolved)
	 - 개발자가 결함 수정을 완료한 상태이다.

	5. 결함 조치 보류(Deferred)
	 - 수정이 필요한 결함이지만 현재 수정할 수 없어 연기된 상태
	 - 우선순위와 일정 등을 고려하여 이후 재오픈을 준비

	6. 결함 종료(Closed)
	 - 결함이 해결되고 테스터와 QA 담당자가 종료를 승인한 상태

	7. 결함 해제(Clarified)
	 - 테스터, 프로그램 리더 및 QA 담당자가 검토한 결과 결함이 아닌 것으로 판명된 상태

< 결함 분류 >

	1. 시스템 결함
	 - 어플리케이션 환경이나 데이터베이스 처리에서 발생하는 결함
		EX.
		 - 비정상적인 종료 또는 중단
		 - 응답 시간 지연
		 - 데이터베이스 오류

	2. 기능 결함
	 - 기획 설계 또는 업무 시나리오 단계에서 발생한 문제이다.
		EX.
		 - 요구사항 미반영 또는 불일치
		 - 부정확한 비즈니스 프로세스
		 - 스크립트 오류
		 - 다른 시스템 연동 오류

	3. GUI 결함
	 - 사용자 화면 설계에서 발생하는 결함
		EX.
		 - UI 비일관성
		 - 부정확한 커서 또는 메시지
		 - 데이터 타입 표시 오류
		
	4. 문서 결함
	 - 기획자, 사용자 및 개발자 간 의사소통과 기록이 원활하지 않아 발생한다.
		EX.
		 - 온라인, 오프라인 사용자 매뉴얼 불일치
		 - 요구사항 분석서와 기능 요구사항의 불일치
		 - 내용이 누락된 불완전한 문서

< 결함 심각도 >
 - 결함이 전체 시스템에 미치는 영향을 수준별로 나타낸 지표

	1. High
	 - 시스템이 중단되거나 더 이상 업무를 진행할 수 없는 결함
		EX.
		 - 핵심 요구사항 미구현
		 - 시스템 다운
		 - 장시간 응답 지연
		 - 시스템 복구 후 데이터 왜곡

	2. Medium
	 - 시스템의 업무 흐름에 영향을 미치는 결함
		EX.
		 - 부정확한 기능
		 - 잘못된 업무 프로세스
		 - 데이터 필드 형식 오류
		 - 데이터베이스 오류
		 - 보안 관련 오류

	3. Low
	 - 시스템 흐름에 직접적인 영향을 미치지 않는 결함
		EX.
		 - 부정확한 GUI
		 - 부정확한 메시지
		 - 오류 메시지 미출력
		 - 화면 문법 또는 철자 오류
		 - 화면 구성 오류


결함 관리 문서 작성 시 스프레드 시트 작성을 권장한다.
결함 관리 목록은 주로 테스트 ID를 기준으로 작성하고 각각의 테스트 ID에 따른 테스트 케이스 ID를 관리하는 것이 바람직하다.
각각의 테스트 수행 결과는 스프레드 시트로 연산하여 전체 테스트 공정을 볼 수 있게 파레토 다이어그램과 연결하는 방법이 바람직하다.
