SQL 처리 흐름
< 구문분석 >
 - SQL문이 사용된 적이 있는지 없는지 판단(공유 풀 영역을 검색하여 판단)
	ㄴ * 공유 풀 영역
	 - 데이터베이스 메모리 안에 있는 공간
	 - 이전에 실행된 SQL문과 실행 계획이 저장될 수 있다. 

 실행이 된 적이 있음 -> 공유 풀 영역에 SQL문이 올라가있을 것이므로 다시 구문분석을 할 필요가 없음
 실행 된 적 없음 -> 구문분석 작업 수행

 - 사용자가 작성한 SQL문장을 DBMS가 이해할 수 있는 형태로 해석하는 과정
 SELECT * FROM EMP WHERE EMPNO = 7369;
 위와 같은 문자열을 보고 DBMS는
 	- SELECT문인지
 	- 문법이 올바른지
 	- EMP 테이블이 존재하는지
 	- EMPNO 컬럼이 존재하는지
 	- 사용자가 권한이 있는지
 같은 내용을 확인함

 구문 분석의 3단계
 1. 문법 검사 : SQL 문법이 맞는지 확인
 2. 의미 검사 : 문법은 맞지만 실제 객체(테이블, 뷰 등)가 존재하는지 확인
 3. 권한 검사 : 사용자가 해당 객체에 접근 가능한지 확인

< 실행단계 >
 - 구문 분석이 끝난 SQL을 실제로 실행하는 단계
 - 구문 분석 단계에서 실행 계획이 만들어졌다면, 데이터베이스는 그 계획에 따라 실제 데이터를 찾거나 변경함
	ㄴ 실행 계획
	??????

		ㄴ 데이터베이스 버퍼 캐시
		 - 디스크에서 읽어온 데이터를 잠시 저장해두는 메모리 공간
		 - 디스크는 데이터를 영구적으로 저장하지만, 속도가 느림
			-> 메모리에 잠시 저장을 해두면 자주 사용하는 정보에 대해 접근이 빨라짐
		
		데이터베이스 버퍼캐시에 존재 -> 꺼내서 사용
		데이터베이스 버퍼캐시에 없음 -> 데이터 파일에서 읽고 버퍼 캐시에 저장(올려둠)

		SELECT가 아닌 DML이라면 버퍼 캐시 영역에서 수정, 삭제, 추가를 한다.
		-> COMMIT을 해야 변경사항이 확정된다.

< SQL 작성 시 고려사항 >
 1. SQL의 특성을 충분히 이해해야 함(DBMS별 작성 방법을 숙지)
 2. 옵티마이저가 실행 계획을 수립한 후 실행된다는 것을 이해해야 함.
	 - 이 조건은 인덱스를 사용할 수 있는가?
	 - 이 JOIN은 어떤 테이블부터 읽는 것이 좋은가?
	 - WHERE의 조건이 너무 넓지는 않은가?
	 - 정렬이 불필요하게 발생하지는 않은가?
 3. 실행 계획에 따라 수행 속도 차이가 크게 발생할 수 있다는 것을 이해해야 함.
 4. 옵티마이저가 비정상적으로 동작한다면, 이를 추적하여 개발자가 원하는 실행 계획으로 동작될 수 있도록 조정하는 과정이 필요함.
	 - 인덱스 추가
	 - SQL의 조건을 변경
	 - JOIN의 순서를 개선
	 - 힌트
		ㄴ ** 힌트 : 옵티마이저에게 SQL을 어떻게 실행할 지 개발자가 직접 지시하는 기능
			- 사용방식 : /*+ */
			- 인덱스를 사용하도록 지시 -> /*+ INDEX(EMP PK_EMP) */
			- 전체 테이블 조회(FULL 힌트) -> /*+ FULL(EMP) */

 - 옵티마이저가 정상적인 실행 계획을 수립할 수 있도록 종합적이고 전략적인 포인트를 SQL에 부여하여 작성해야 한다.

 5. 
 - 불필요한 전체 조회를 줄인다.
 - 인덱스를 사용할 수 있는 형태로 작성한다.
 - 조인 조건을 정확히 작성한다.
 - 필요한 칼럼만 조회한다.

 6. 좋은 SQL은 결과를 추론하고 집합적으로 접근해야 한다.
 - 내가 최종적으로 필요한 데이터는 무엇인가?
 - 몇 건 정도 조회될 것인가?
 - 어떤 조건으로 데이터를 줄일 수 있는가?
 - 조인이 필요한가?
 - 정렬이 꼭 필요한가?
 - 중복 제거가 필요한가?


< SQL 성능 최적화를 위한 유틸리티 활용 >
1. TKPROF
 - 실행되는 SQL 문장에 대해 분석 정보를 제공하여 사용자가 특정 SQL문장을 어떻게 사용해야 할 것인지에 대한 가이드라인을 제공하는 도구

2. EXPLAIN PLAN
 - 사용자들이 SQL문의 액세스 경로를 확인하여 성능 개선을 할 수 있도록 SQL문을 분석하고 해석하여 실행계획을 수립하고, 관련 테이블에 저장하도록 지원해주는 도구

< 데이터 조작 프로시저 성능 개선하기 >
 - 업무 분석가에 의해 정의된 요구사항을 기준으로, 성능 측정 도구를 활용하여 데이터 조작 프로시저의 성능을 측정한다.

 1. 성능 측정을 위한 기준 요구사항 식별
 - 응답 시간, 처리 건수, 리소스 사용량 등 정량적 성능 목표를 분석하고, 테스트 대상 프로시저별 성능 기준 정의하기

 2. 성능 측정 도구 설정
 - 성능 도구(TKPROF 등)를 설정하고 Trace 로그 수집을 준비한다.
	ㄴ ** Trace 파일
	 - Oracle이 SQL 실행 과정을 기록한 로그 파일이다.
	 	ㄴ정보
		 - 언제 실행했는지
		 - 몇 번 실행했는지
		 - 몇 개의 블록을 읽었는지
		 - 몇 개의 행을 조회했는지
		 - CPU를 얼마나 사용했는지
		 - 디스크를 얼마나 읽었는지

 - ALTER SESSION SET SQL_TRACE = TRUE;
 이후에 SQL들을 진행
 - ALTER SESSION SET SQL_TRACE = FALSE;

 3. 대상 프로시저를 실행하고 측정 데이터를 수집한다.
 - 테스트용 데이터를 사용하여 프로시저를 실행하고, 실행 결과 및 Trace 로그를 수집한다.

 4. 측정 결과를 분석하여 실행 성능을 평가한다,
 - 수행 시간, 블록 읽기 수, CPU 사용량 등을 바탕으로 성능을 분석하고, TKPROF 결과 또는 APM 지표를 검토한다.
	ㄴ ** APM(Application Performance Monitoring)
	 - 운영 중인 시스템에 대한 가용성 확보, 다운타임 최소화 등을 통해 안정적인 시스템 운영을 위하여 부하량과 접속자 파악 등 장애 진단을 목적으로 사용하는 성능 모니터링 도구

 5. 실 데이터를 기반으로 테스트를 수행하여 데이터 조작 프로시저의 성능에 영향을 주는 병목(jamming) 구간을 파악한다.
	
	(1). 실 데이터를 반영한 테스트 환경을 구성한다.
	- 운영 데이터의 복사본 또는 유사 데이터를 준비하여 성능 테스트 환경을 구성한다.

	(2). 테스트 시나리오를 설계한다.
	- 대량 처리, 복합 조건, 동시성 등 다양한 상황을 반영하여 테스트 시나리오를 작성한다.

	< 주문 처리 프로시저 >
	CALL process_order(회원번호, 상품번호, 주문수량);
 	 - 회원 존재 여부 확인
 	 - 상품 재고 확인
	 - 주문 데이터 insert
	 - 상품 재고 update
	 - 결제 데이터 insert
	 - 처리결과를 반환

	테스트 시나리오
	 - 정상 주문이 들어왔을 때 정상 처리 되는가?
	 - 재고가 부족하면 주문이 실패하는가?
	 - 주문이 1건이 아니라 10만건이면 성능이 괜찮은가?
	 - 여러 사용자가 동시에 주문하면 재고가 꼬이지는 않는가?
	 - 복합 조건 검색이 느려지지 않는가?

	(3). 테스트를 수행하고 성능 로그를 수집한다.
	 - PL/SQL 블록 싫애 또는 SQL Script 반복 실행을 통해 성능 데이터를 수집한다.

	(4). 병목 지점을 식별
	 - 실행 계획을 분석하여 인덱스 미사용, Full Scan, 테이블 조인 방식 등을 점검하고, 통계 정보 최신화 여부를 확인한다.

	(5). 성능 저하 원인을 문서화한다.
	 - 병목이 발생한 SQL과 원인을 정리하고, 개선 필요 항목을 도출하여 분석 보고서를 작성한다.

 6. 테스트 결과와 정의된 요구사항을 기준으로 데이터 조작 프로시저의 성능에 따른 이슈를 해결한다.

	(1). 속도를 저하시키는 SQL 구문을 재작성하여 성능을 개선한다.
	 - WHERE 절 최적화, 서브쿼리 정리, IN 대신 EXISTS 사용 등을 통해 쿼리 성능을 향상한다.

	(2). 실행 계획 개선
	 - 옵티마이저 힌트를 적용하거나, Driving 테이블을 변경하여 최적의 실행 경로를 유도한다.
		ㄴ ** Driving 테이블
		 - 조인을 수행할 때 가장 먼저 읽는 테이블(From에 적어둔 메인 테이블)

	(3). 인덱스를 재구성한다.
	 - 새로운 인덱스를 추가하거나 기존 인덱스를 조정하여 접근 효율성을 높인다.

	(4). 시스템 리소스 병목 구간을 조정한다.
	 - Shared Memory, CPU, I/O 등 인프라 병목 구간이 원인일 경우 시스템 관리자의 협조를 통해 시스템 설정을 최적화한다.

	(5). 개선 후 동일한 테스트로 효과를 검증한다.
	 - 동일한 테스트를 반복 실행하여 개선 전후 성능 차이를 수치로 비교하고 효과를 검증한다.

	(6). 성능 개선 결과를 문서화하고 공유한다.
	 - 개선 전후 비교, 변경 내역, 테스트 결과를 정리하여 성능 개선 보고서를 작성한다.

2. 논리 데이터 모델의 구성 요소 중, 데이터베이스에 명시된 규정에 따라 RELATION이 가질 수 있는 유효한 데이터 값의 범위를 제약하는 규칙을 의미하는 용어를 작성하시오.

3. 관계 데이터베이스 모델에서 상위 테이블의 기본키(Primary Key)를 참조하여 테이블 간의 연결고리 역할을 하는 속성을 무엇이라고 하는지 작성하시오.
 - 외래키(Foreign Key)

4. 논리 데이터 모델링의 주요 목적 중 하나는 데이터의 중복을 제거하여 이상 현상(Anomaly)을 방지하는 것입니다.
데이터베이스에서 발생할 수 있는 이상 현상(Anomaly)의 3가지 종류를 제시하고, 각각의 개념을 간략히 설명하시오.
 - 삽입 이상 : 데이터를 삽입할 때 데이터 불일치가 일어나는 등의 상황으로 무결성이 깨지는 것
 - 수정(갱신) 이상 : 데이터를 수정할 때 같은 데이터가 있음에도 함께 수정되지 않아 데이터 불일치가 일어나 무결성이 깨지는 것
 - 삭제 이상 : 데이터를 삭제할 때 필요한 다른 데이터도 함께 삭제되어 무결성이 깨지는 것

5. 데이터베이스 설계 과정에서 '개체 무결성(Entity Integrity)'과 '참조 무결성(Referential Integrity)'은 데이터의 정확성을 보장하는 핵심 규칙입니다.
이 두 제약조건의 개념과 위배되지 않기 위한 세부 규칙을 비교하며 서술하시오.

개체 무결성
 - NULL값이 들어가면 안되고, 중복되는 값이 들어가면 안된다.(PK값이어야 함)

참조 무결성
 - 외래키 값은 참조 대상이 되는 관계 릴레이션의 기본키 값과 동일하거나, 혹은 NULL이어야 한다.

- CASCADE : 삭제 및 수정을 시도했을 때, 참조된 다른 테이블의 값 또한 연쇄적으로 삭제 또는 수정됨
- RESTRICT : 삭제 및 수정을 시도했을 때, 참조된 다른 테이블의 값이 있다면 삭제가 제한됨
- NULLIFY : 삭제 및 수정을 시도했을 때, 삭제는 정상적으로 진행하고 참조된 다른 테이블의 관련값은 NULL로 설정됨


6. 논리 데이터 저장소 확인 단계에서는 관계형 데이터 모델의 설계 품질을 높이기 위해 '정규화(Normalization)' 과정을 검토합니다.
제1정규형(1NF)부터 제3정규형(3NF)까지의 정규화 과정을 각 단계별 변환 조건(만족해야 하는 기준)을 포함하여 단계적으로 서술하시오.

 - 1NF : 하나의 컬럼에는 한 종류의 값만 들어가야 함(모든 테이블의 값이 원자값이어야 한다.)
 - 2NF : 1차 정규형을 만족하면서, 기본키키가 아닌 모든 속성이 기본키에 완전 함수적 종속을 만족해야 함
	(부분 함수 종속 제거)
 - 3NF : 2차 정규형을 만족하면서, 기본키가 아닌 모든 속성이 기본키에 대한 이행 함수 종속성을 가지지 않아야 한다.


7. 관계형 데이터 모델에서 릴레이션의 행(Row)를 뜻하는 용어로, 카디널리티(Cardinality)의 수와 직결되는 이것은 무엇인가?

8. 어떤 릴레이션 R에서 속성 X의 값 각각에 대해 속성 Y의 값이 오직 하나만 연관되어 있을 때, Y는 X에 '이것'되어있다고 한다. 무엇인가?
 - 함수적 종속성

 정규화가 조회(Select) 성능을 떨어뜨리는 이유를 연산(Operation)의 관점에서 서술하시오.
 - 종속성을 다 풀어버린 상태의 완전 종속 테이블이 여러개 연결되어 있다고 치면, 결국은 관련 정보이기에 테이블을 다시 조인하여 정보 조회를 진행할 가능성이 높다. 즉 무분별한 정규화는 조회 시 조인 과정이 늘어나게 되고, 이는 디스크와 CPU 자원을 많이 소모하게 되어 시스템의 성능 저하를 일으킨다.

11. 제2정규형(2NF)의 정의를 설명하고, 테이블이 제1정규형(1NF)은 만족하지만 제2정규형(2NF)을 만족하지 못할 때 발생하는 문제점을 복합키(Composite Key) 관점에서 서술하시오.
 - 제2정규형은 제1정규형인 컬럼의 원자성을 만족하면서, 몇 컬럼이 복합키의 일부에만 종속되어있는 관계인 부분 함수 종속을 제거한 형태이다.
  ex. (학생번호, 강사번호) -> (강사명)에서 강의명은 강사번호에만 관련되어 종속됨

 - 제1 정규형은 만족하지만 제2정규형을 만족하지 못하면, 이 부분 함수 종속이 해결되지 않아 두 키 중 하나인 정보에만 연관된 값이 삽입, 수정 또는 삭제될 때, 다른 행에 동일한 값이 필요없음에도 남아있거나, 필요함에도 삭제되거나, 어느 행은 정보가 변경되었지만 다른 행은 변경되지 않는 등의 이상 현상이 발생하게 된다.

16. 논리적 데이터 모델을 물리적 데이터 모델로 변환할 때, 시스템의 성능 향상을 위해 테이블 '수평 분할(Horizontal Partitioning)'을 수행하는 기준과 이로 인해 얻을 수 있는 장점을 데이터 검색 속도 관점에서 서술하시오.

 - 수평 분할 : 행 수가 너무 많아 성능이 저하되는 대용량 테이블을 특정 컬럼 값의 범위를 기준으로 행 단위의 분할을 진행하는 것을 의미한다. 이로 인해 데이터를 검색할 때 전체 테이블을 뒤지지 않고 해당 조건이 속한 파티션 영역에만 집중 검색을 진행하므로 디스크 물리적 탐색 범위가 줄어들어 검색 속도가 획기적으로 상승한다.

수평 분할의 종류

 - 범위 분할 : 년도, 월 등 DB 관리자가 지정한 특정 범위를 통해 분할한 것을 의미한다. 해당 분할을 통해 원하는 시점 또는 조건의 정보를 빠르게 체크할 수 있다.
 - 해시 분할 : 시스템이 직접 자체적 기준에 따라 데이터량을 일정하게 분할한 것을 의미한다. 이 경우 데이터량의 편중이 사라져 데이터 보관량을 균일하게 유지할 수 있다.
 - 조합 분할 : 범위 분할과 해시 분할의 장점을 섞은 분할 방식으로, 관리자가 범위를 지정한 파티션 내부에 서브파티셔닝을 통해 해시 분할을 하거나, 반대의 상황으로 분할한 것을 의미한다. 이 경우 범위 분할과 해시 분할의 장점을 모두 가져와 원하는 범위 검색에도 용이하고, 데이터량도 편중 없이 균일하게 유지된다.

EXPLAIN PLAN : SQL을 실제로 수행하지 않고 옵티마이저가 수립한 데이터 액세스 경로와 '수행 순서 계획표'만을 PLAN_TABLE에 저장하여 예측하는 도구
