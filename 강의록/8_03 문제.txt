문제 1. 연계 요구사항 분석
[상황]

A 쇼핑몰과 B 물류시스템을 연계하려고 한다.

쇼핑몰에서는 주문이 완료되면 주문번호, 상품명, 수량을 물류시스템으로 전송해야 한다.

프로젝트 책임자는 개발을 시작하기 전에 반드시 연계 요구사항 분석을 수행하도록 지시하였다.

[조건]

다음 내용을 모두 포함하여 서술하시오.

요구사항 분석을 먼저 수행해야 하는 이유 4가지
 1. 사용자의 요구사항을 구체화하기 위함이다.
 2. 형식, 범위, 주기, 전송 방식을 명확하게 하여 데이터 손실 및 오류를 방지하기 위해서이다.
 3. 프로그램을 확장할 때 어려움이 없고 오류를 예방하기 위해서이다.
 4. 서비스 품질을 보장하기 위해서이다.

요구사항 분석 절차를 순서대로 작성
 1. 현행 시스템 및 운영 환경 파악 : 쇼핑몰과 물류시스템의 하드웨어, 소프트웨어(프로그램), 각 DB의 ERD를 확인
 2. 사용자 요구사항 수집 : 쇼핑몰 주문에 관련된 인터뷰, 설문조사, 체크리스트, FGI 등을 수집한다.
 3. 연계 데이터 분석 : DB의 데이터를 전달할 때 사용하게 될 연계 데이터의 형식, 길이, 프로토콜 등을 확인한다.
 4. 결과 정리 : 위의 단계에서 분석한 결과를 정리하여 문서로 작성한다.

요구사항 분석이 완료되면 작성되는 산출물 3가지를 작성
 - 요구사항 분석서, 인터페이스 정의서, 회의록

 1. 시스템 구성도 : 시스템이 어떻게 구성되어 있는지 확인하여 데이터 송수신에 어려움이 없도록 진행할 수 있음
 2. 응용 어플리케이션 구성 : 응용 어플리케이션을 확인하여 데이터 송수신에 어떠한 도움이 될 수 있는지 확인할 수 있음
 3. ERD : 엔티티의 관계성을 확인하고 연계 데이터 구성을 위해 필요한 정보를 어떻게 추출할 수 있는지 알 수 있음

[상황]

A회사는 매일 새벽 2시에 하루 동안 발생한 주문 데이터를 B회사에 전달한다.

전송 데이터는 약 80만 건이며 실시간 처리는 필요하지 않다.

운영 DB의 성능 저하를 최소화해야 한다.

[조건]

다음 내용을 모두 포함하여 서술하시오.

가장 적합한 생성/추출 방식을 선택 : 파일
선택한 이유 3가지
 - 대량 데이터 전송에 적합하다
 - 실시간 전송이 어렵지만 해당 상황에서는 실시간 처리가 필요없다.
 - 다양한 시스템에서 사용이 가능하다.

메시지 방식을 선택하지 않은 이유
 - 구현이 복잡하고 실시간 처리를 위한 방식이므로 하루 한 번 배치 전송을 진행하는 환경에서는 적합하지 않다.

문제 3. 인터페이스 테이블 활용
[상황]

쇼핑몰 운영 DB에는 다음 데이터가 저장되어 있다.

주문번호   상품명   고객명   결제금액
1001   노트북   김철수   120만원

물류시스템에서는 주문번호와 상품명만 필요하다.

운영 DB를 직접 조회하지 않고 인터페이스 테이블을 이용하기로 하였다.

[조건]

다음 내용을 모두 포함하여 서술하시오.

인터페이스 테이블을 사용하는 이유 3가지
 - 데이터 유효성 검증이 가능하다.
 - 중간 인터페이스 테이블을 통해 필요한 정보만 추출하여 전달이 가능하다.
 - 실시간으로 송신한 뒤 정보를 모아 한 번에 처리할 수 있다.(대량 데이터 처리 가능) 이로 인해 운영 DB의 성능 저하를 방지할 수 있다.
 - 운영DB의 오염을 방지한다.(데이터의 직접 접근하여 데이터가 위변조되는 상황 방지)

인터페이스 테이블의 컬럼 작성
 - 주문번호, 상품명만 작성한다(나머지 정보는 전달받지 않는다)

운영 DB를 직접 조회하면 발생하는 문제 3가지
 - 보안성 : 공개하지 않아야 하는 정보까지 유출될 가능성이 있다.
 - 데이터 검증 과정 누락으로 인한 DB 오염 : DB의 데이터를 아무런 유효성 검증이나 재처리 없이 사용하면 데이터의 위변조 및 의도되지 않은 데이터 변화가 일어나 DB 데이터의 정합성이 깨지거나 잘못된 정보의 저장을 걸러내지 못할 수 있다.
 - 송수신 시스템의 처리 시간 분리가 불가능 : 데이터 수신을 실시간으로 받아 바로바로 DB에 저장하게 되므로, 송수신 과정이 많아지고 정보의 대량 처리 시 네트워크의 부하로 이어지게 된다.

 - 시스템 속도가 느려질 수 있다
 - 운영 데이터를 잘못 수정할 위험이 있다
 - 필요한 데이터만 추출하기 어렵다

문제 5. 연계 서버 및 송신 어댑터
[상황]

ERP 시스템은 FTP를 이용하여 데이터를 전송한다.

CRM 시스템은 REST API를 사용한다.

또한 데이터 형식도 서로 다르다.

회사는 연계 서버를 이용하여 데이터를 처리하려고 한다.

[조건]

다음 내용을 모두 포함하여 작성하시오.

연계 서버가 수행해야 하는 기능 5가지
 - 프로토콜을 FTP -> REST API로 변환하는 기능
 - 반대 시스템에 맞게 연계 데이터의 형식을 변경하는 기능
 - 메시지 라우팅 기능
 - 통합 모니터링 및 로깅 기능
 - 보안 기능
 - 재처리 기능

 - 송신 시스템은 FTP를 사용하고 수신 시스템은 REST API를 사용하므로 서로 다른 통신 방식을 사용할 수 있도록 변환해야 하기 때문이다.

문제 12. 연계 데이터 암호화 설계
[상황]

A 쇼핑몰과 B 물류시스템이 데이터를 연계하고 있다.

현재 개발팀은 다음과 같은 방식으로 구현하였다.

고객 이름
주민등록번호
휴대전화번호
배송 주소

를 모두 인터페이스 테이블에 저장한 후 그대로 수신 시스템으로 전송하고 있다.

하지만 보안 점검 결과 다음과 같은 문제점이 발견되었다.

주민등록번호가 평문으로 저장된다.
암호화 Key가 소스코드에 작성되어 있다.
암호화 후 데이터 길이가 늘어나 컬럼 길이 초과 오류가 발생한다.
송신 시스템과 수신 시스템에서 서로 다른 암호화 알고리즘을 사용하고 있다.

프로젝트 책임자는 연계 데이터 보안을 전면 개선하도록 지시하였다.

[조건]

다음 내용을 모두 포함하여 서술하시오.

현재 시스템의 보안 문제점을 4가지 작성하시오.
 - 주민번호가 평문으로 저장되어 있다.
 - 암호화 KEY가 소스코드에 저장되어 있다.
 - 암호화 후 데이터 길이를 고려하지 않았다.
 - 송/수신 시스템의 암호화 방식이 서로 다르다.

연계 데이터 암호화 방식을 결정할 때 고려해야 할 사항을 5가지 작성하시오.
 - 어떤 데이터를 암호화 할 것인가?
 - 어떤 알고리즘을 사용할 것인가?
 - KEY를 어떻게 관리할 것인가?
 - 어느 구간에서 암호화 할 것인가?
 - 어느 구간에서 복호화 할 것인가?

데이터 길이를 수정해야 하는 이유를 작성하시오.
 - 암호화를 진행하면 데이터 길이가 늘어 컬럼 길이 초과 오류로 인해 데이터의 손실이 생길 수 있다. 이는 데이터의 변조로 귀결되므로 데이터 최대 길이를 미리 늘려두어야 한다.


암호화 라이브러리를 설치해야 하는 이유를 작성하시오.
 - 송/수신 시스템에서 동일한 암호화 API를 사용하여 암호화와 복호화를 수행하기 위해 필요하다.


송신 시스템과 수신 시스템의 암호화 방식이 다른 경우 처리 절차를 순서대로 작성하시오.
 - 송신 시스템에서 데이터를 암호화한다
 - 암호문을 전송한다
 - 수신 시스템에서 송신 시스템의 방식으로 복호화한다
 - 수신 시스템에서 운영 DB의 암호화 방식으로 다시 암호화한다.
 - 새롭게 암호화된 데이터를 운영DB에 저장한다.
