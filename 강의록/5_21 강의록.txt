4. 요구사항의 시스템화 타당성 분석

 - 서버가 감당 가능한지, 현재 기술로 가능한지, 비용은 얼마나 드는지, 유지보수가 가능한지
 - 개발 전에 기술적으로 가능한지 검토하는 단계

기술적 타당성 검토의 흐름
성능 및 용량 산정 적정성 검토
 - 예상 사용량을 산정한다.
 - 과거 유사 프로젝트의 사용량을 반영하여 필요하면 재조정
 - 요구사항 중 속성이 성능인 비기능 요구사항을 만족하는지 판단
	ㄴ 요구사항 미충족 or 충족 시
		-> 다시 조정한다. / 요구사항을 만족한다고 체크

시스템 간 상호 운용성 검토
 - 서로 다른 목적을 가진 두 개 이상의 시스템이 정보를 주고받고 서비스를 공유하면서 정상적으로 동작할 수 있는지 검토

	연동 대상 시스템이 무엇인지 확인
		 - 어떤 시스템과 연결해야 하는지 알아야 하기 때문
		ex. 결제 시스템, 문자 시스템, 보험 시스템, 택배 시스템...

	서로 정보를 주고받을 수 있는지 확인
		 - 데이터 형식이 다르면 통일해야 전달(요청, 응답)이 용이하고, 나중에 누락 정보가 없게 처리가 가능
		 - 나는 USER, 외부 시스템은 MEMBER로 통일

	서비스 제공 방식이 맞는지 확인
		 - 우리 서비스 : 사용자가 요청할 때 실시간으로 제공
		 - 외부 시스템 : 하루에 1회만 제공
			-> 괴리가 생김.
		 - 판단 : 동작 방식의 차이가 발생할 수 있다. 
			-> 추가적인 처리가 필요하다

	최종적으로 연동 가능 여부 판단
	 - 요구사항을 실제 구현 가능한지 결정
	ex. 요구사항 : 사용자가 주문하면 즉시 배송상태를 확인할 수 있어야 한다.
	검토결과 : 택배 시스템은 하루 1회만 정보 제공
	판단 : 실시간 제공은 현실적으로 불가능하다
	결과 : 요구사항의 수정이 필요하다.

	수정 예시
	요구사항 수정
	사용자는 배송 상태 정보를 하루 1회 갱신된 기준으로 확인할 수 있다.

	또는
	
	사용자는 매일 오전 9시에 갱신된 배송 상태 정보를 확인할 수 있다.

IT 시장 성숙도 및 트렌드 부합성 검토
 - 시장 성숙도
	: 사용하려는 기술이나 제품이 시장에서 충분히 검증되었는지 확인하는 것

	확인하는 항목
	1. 사용하는 기업 수
	2. 사용하는 사용자
	3. 기술 지원 여부
	4. 시장 점유율

 - 사용할 기술 확인
	: 어떤 기술을 사용할 예정인지 알아야 함

 - 시장 성숙도 확인
	: 현재 안정적으로 사용되는 기술인지 판단

 - 기술 발전 방향 확인
	: 앞으로도 사용될 기술인지 확인

 - 요구사항 적합 여부 판단
	: 향후 유지보수가 가능한지 판단하기 위해

기술적 위험 분석 검토
 - 요구사항을 구현하기 위해 사용할 기술이 문제를 일으킬 가능성이 있는지, 문제가 생겼을 때 영향이 얼마나 큰지를 판단하는 과정
	
	 - 위험성 목록
	난이도 : 개발이 너무 어렵다
	숙련도 : 조직 안에서 이 기술을 써 본 사람이 없다.
	의존성 : 특정 업체 기술에만 의존
	비용 : 라이선스 비용이 예상보다 크다
	비호환성 : 기존의 아키텍처와 맞지 않다.
	지원 부재 : 외부지원을 받을 수 없다.

복잡성
 - 적용하려는 기술이 안정성, 시장성, 개방성을 해칠 수 있는 요소를 가지고 있는지 보는 것

 - 요구사항을 기능적으로 정리하고, 시스템이 수행해야 할 구조와 동작을 논리적으로 표현한 모델

분석 모델을 검증
- 실제 요구사항을 반영하고 있는지
 - 개발을 위해 적절한지

검토 흐름

1. 요구사항 작성
2. 분석모델 작성
3. 검증 수행
4. 적합시 개발 실행

분석 모델을 검토해야 하는 이유
1. 요구사항이 충실하게 반영되었는지(누락 or 과한 해석이 없는지)
2. 오해나 불일치 방지
3. 추가 의견 제시를 통한 보완
4. 개발 가능성과 구체성 확보
5. 프로젝트 리스크 사전 제거

정합성의 개념
1. 논리적으로 일관되어야 한다.
2. 모순이 없어야 한다.
3. 중복되는 내용이 없어야 한다
4. 충돌되는 내용이 없어야 한다.
5. 구조적 불일치가 없어야 한다.

검토 관점

FB-002		추천 도서 기능 추가 요청		미반영	사용자 대여 / 추천 알고리즘 구현으로 인해 일정 영향이 생기며,
											 프로젝트 범위에 포함되지 않음



분석모델의 시스템화(분석 모델을 통해 개발을 진행함) 타당성 분석
 - 분석 모델을 통해 실제 시스템 개발을 진행함에 있어 운용 상황 ,시장 상황 및 기술적 타당성이 결여되어 있지 않은지 판단
	
	* 검토 관점

	필요한 자원
	 - 시스템을 구현하고 운영하기 위해 얼마나 많은 컴퓨터 자원과 개발 자원이 필요한지 확인

	상호 운용성
	 - 우리 시스템이 다른 시스템과 정보를 주고받을 수 있는지 의미

	시장 성숙도 및 트렌드 부합성 검토
	 - 사용하는 기술이 충분히 안정적이고 많이 사용되고 있는지 확인하는 것이다.
	 - 트렌드 부합성은 현재 개발 환경이나 산업 흐름에 맞는 기술인지 확인하는 것
	 - 기술을 잘못 선택하면 개발 중 문제가 생길 수 있음

	 기술적 위험 분석
	 - 개발 과정에서 문제가 도리 수 있는 위험 요소를 미리 찾는 것.


	* 타당성 분석 수행
	순서
		1. 분석모델까지 요구사항 추적표를 작성하고, 타당성 검토 의견 속성을 추가한다.
		2. 작성된 요구사항 추적표에 타당성 검토 의견을 작성한다.
		
	* 각 모델별로 유의해야 할 점
	유스케이스 모델 타당성 검토
	 - 관련 액터들이 너무 많지는 않은지
	 - 이벤트 흐름과 예외 흐름이 지나치게 복잡하지는 않은지

	개념 수준 분석 클래스 모델 타당성 검토
	 - 너무 많은 클래스 모델들이 도출되지 않았는지

	** 개념 수준 분석 클래스 모델
	 - 요구 사항을 읽고 시스템에서 관리해야 할 중요한 사람, 사물, 정보, 업무 개념을 클래스로 뽑은 것
	ex. 도서 대여 시스템
	요구사항
	회원은 도서를 검색하고 대여할 수 있다.
	회원은 대여한 도서를 반납할 수 있다.
	시스템은 대여 내역을 관리한다.

	요구사항에서 나온 개념		개념 수준 분석 클래스 후보
	회원						Member
	도서						Book
	대여						Rental
	반납						Return
	대여내역					RentalHistory

	분석 클래스 모델 타당성 검토
	 - 요구사항을 만족시키기 위한 경계/제어/엔티티 클래스들이 너무 많지는 않은지
	 - 관계가 너무 복잡하지는 않은지
	 - 관리해야할 속성들이 지나치게 많은지 검토

	** 분석 클래스 모델
	 - 요구사항을 만족시키기 위해 필요한 클래스들을 역할에 따라 정리한 모델
		경계 클래스 : 사용자나 외부 시스템과 만나는 클래스
		제어 클래스 : 기능 흐름과 처리 순서를 담당하는 클래스
		엔티티 클래스 : 실제 업무 데이터를 저장하고 관리하는 클래스

	이후 타당성 분석 결과를 이해관계자가 검증한다.
		1. 타당성 분석 결과를 관련 이해관계자에게 배포하여 사전 검토를 요청한다.
		2. 관련 이해관계자가 모여 분석모델 타당성 분석 결과를 검증한다.
		3. 타당성 분석 결과에 이견이 있는 경우 프로젝트 관리자의 중재 하에 합의를 도출한다.

	관련 이해관계자 검증을 거친 타당성 분석 결과를 확인하고 배포 및 공유한다.
		1. 관련 이해관계자 검증을 거친 타당성 분석 결과를 의사 결정자가 확인한다.
		2. 의사 결정자가 확인한 타당성 분석 결과를 이해관계자에게 배포하여 공유한다.
