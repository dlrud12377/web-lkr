 < 복습 >
 - MySQL 기반에서는 스키마 = 데이터베이스
 - 스키마 : 데이터를 어떻게 저장할것인지에 대한 "설계도"이다.

	< 스키마의 구성요소 >
		- 테이블(table, 표)
		- 뷰(view)
		- 인덱스(index)
		- 트리거(trigger)
		- 저장 프로시저(Procedure)

	< 스키마를 사용하는 이유 >
		1. 데이터 구조를 정리하기 위해
		- 구조를 정해서 일관성을 유지

		2. 데이터 관리 단위로 사용하기 위해
		- 프로젝트별로 DB를 나눌 수 있다. (ex. 쇼핑몰 / 게시판 / 회원관리)

		3. 접근 권한 관리
		- 특정 스키마만 접근하도록 설정 가능

	< 데이터베이스 - 3가지로 나뉨>
		1. 외부 스키마
		- 사용자 입장에서 보는 구조(화면에 보이는 데이터)

		2. 개념 스키마
		- 전체 데이터 구조(DB 설계자 관점)

		3. 내부 스키마
		- 실제 저장 방식(디스크에 어떻게 저장되는지)

	Data : 가공되지 않은 단순한 사실이나 값
	DB : 데이터를 체계적으로 저장해놓은 공간
	DBMS : 데이터베이스를 관리하는 프로그램(소프트웨어)

	< DBMS의 종류 >
	1. 계층형 데이터베이스
	- 트리 구조로 데이터를 저장하는 방식
	- 부모 : 자식 = 1 : N(다수) 관계만 가능
	- 구조가 단순하다
	- 변경이 어렵다.

	2. 네트워크형 데이터베이스
	- 데이터를 그래프 형식으로 연결하는 방식
	- N : N 관계가 가능하다
	- 계층형보다는 유연하다
	- 구조가 복잡하다
	- 여러 개의 연결을 허용하는 DB

	3. 관계형 데이터베이스
	- 테이블 형태로 데이터를 저장하는 방식
	- 가장 많이 사용됨
	- SQL을 사용
	- 데이터의 무결성을 보장한다

	4. 객체지향형 데이터베이스
	- 객체(Object) 형태로 데이터를 저장
	- Java, C++ 객체 그대로 저장 가능하다.
	- 복잡한 데이터 처리에 유리
	- 사용 빈도는 낮다.
 
	5. NoSQL(Not Only SQL - SQL만으로 관리하지 않는다 / 복합적인 관리)
	- 관계형이 아닌 다양한 방식의 DB
	
	key - value

	Document
	- JSON

	Column
	- 컬럼 중심 저장

	Graph
	- 관계 중심

	- 대용량 처리에 강함
	- 속도가 빠름
	- 유연한 구조

 < SQL > - Structured Query Language
 - DBMS 상태에서 데이터를 읽고 쓰고 삭제하느 등 데이터를 관리하기 위한 일종의 프로그래밍 언어이다.

 < 데이터 정의어 > DDL - Data Definition Language
- 데이터베이스 객체를 관리하는 언어
- 테이블, 속성, 제약조건, 뷰
- CREATE : 데이터베이스 객체 생성에 사용
- DROP : 삭제에 사용
- ALTER : 수정 시 사용
- TRUNCATE : 테이블은 유지하고 데이터를 통째로 삭제

데이터베이스 생성
CREATE DATABASE IF NOT EXISTS 데이터베이스 이름
CHARACTER SET = utf8mb4
COLLATE = utf8mb4_unicode_ci


CHARACTER SET
이 데이터에서 문자를 저장할 기본 문자셋(Encoding)을 지정
utf8mb4가 MySQL에서 가장 안전한 유니코드 문자셋이다.

COLLATE
정렬과 비교의 기준을 설정

ci : case insensitive(대소문자 구분 없음)

테이블
- 행과 열로 이루어진 데이터의 집합
- 테이블끼리 관계를 맺고, 제약조건이 추가되서 릴레이션이라고도 부름

행(row)
- 가로로 묶은 데이터셋
- 튜플, 레코드라고도 부름
- 행의 개수를 '카디널리티'라고 부름

열(column)
- 세로로 묶은 데이터 셋
- 그 테이블의 속성(attribute)을 의미함

제약조건
- 문제가 되는 데이터를 테이블에 추가할 수 있도록 제한하는 조건
- 테이블을 만들면서 설정할 수 있고, 추후에 생성하거나 변경할 수도 있다.

PRIMARY KEY(기본키)
- 데이터에 값이 있어야 하고, 겹쳐서는 안된다.

NOT NULL
- 해당 속성에는 반드시 값이 들어가야 한다.

UNIQUE
- 속성에 들어가는 값은 유일해야 한다.

FOREIGN KEY(외래키)
- 다른 테이블의 기본키 값을 참조하는 제약조건

CHECK
- 속성에 들어갈 수 있는 데이터의 조건을 설정하는 제약조건

DEFAULT
- 값을 입력하지 않았을 때 자동으로 들어가는 기본값을 설정

CREATE TABLE 테이블명(
속성명1 자료형(IN-LINE 제약조건),
속성명2 자료형,
...

);

데이터베이스 객체의 수정
ALTER

컬럼의 추가
ALTER TABLE 테이블명 ADD COLUMN 컬럼명 자료형;

컬럼의 삭제
ALTER TABLE 테이블명 DROP COLUMN 컬럼명; (삭제이니 자료형은 필요없음)

컬럼명 변경
ALTER TABLE 테이블명 RENAME COLUMN 기존컬럼명 TO 변경컬럼명;

자료형의 변경
ALTER TABLE 테이블명 MODIFY COLUMN 컬럼명 자료형; // not null, unique도 컬럼 속성이므로 modify로 진행

제약조건 추가
ALTER TABLE 테이블명 ADD 제약조건 종류(제약조건 추가할 컬럼명);

제약조건 삭제
ALTER TABLE 테이블명 DROP 제약조건 종류(제약조건 삭제할 컬럼명);
- 기본키(PRIMARY KEY)의 경우는 이름 없이 삭제가 가능
- 나머지 제약조건은 이름을 명시해줘야 한다.(이름을 정하지 않았으면 자동 생성된 이름을 정보에서 찾아야 함)

- NOT NULL과 DEFAULT는 속성의 변경으로 취급하기 때문에 MODIFY를 사용한다.
ALTER TABLE 테이블명 MODIFY 컬럼명 데이터타입;

무결성
- 데이터베이스에 저장된 데이터가 현실 세계의 실제값과 일치하는 정확성을 의미한다.

	1. 개체 무결성
	- PK 설정된 컬럼은 반드시 고유한 값을 가져야 한다. 그리고 NULL이 될 수 없다. (PK = NOT NULL & UNIQUE)

	2. 참조 무결성
	- 외래키(FK)값은 NULL이거나, 반드시 참조하는 테이블의 PK에 들어있는 값과 일치해야 한다.
	- 존재하지 않는 값은 외래키로 저장할 수 없다.

	3. 도메인 무결성
	- 특정 속성의 값이 미리 정의된 유효한 값 범위 안에 있어야 한다.

	4. 사용자 정의 무결성
	- 사용자가 논리적으로 필요한 규칙을 직접 정의하는 것
	- 나이는 음수가 들어올 수 없다. 가입일은 오늘 이후일 수 없다 등등


식별 -> 값이 겹치면 안됨
PK -> 값이 없으면 안되고, 겹치면 안됨
FK -> PK에 들어있는 값을 참고 -> 겹치는 값이 생길수도 있음

 < 정규화 >
 - ERD 내에서 중복 요소를 찾아 제거해나가는 과정

 1차 ~ 5차 정규화가 있음(보통은 3차 정도까지 진행)

	1. 1차 정규화 : 하나의 컬럼에 하나의 값만 있어야 한다
		ex. 철수 / 19 / 수학, 과학 -> 철수 / 19 / 수학, 철수 / 19 / 과학

	2. 2차 정규화 : 1 정규화를 만족하면서 기본키의 일부에만 의존하는 속성을 분리한다.
		ex. 과목과 나이는 상관이 없음 -> 분리
		철수 / 19  //  철수 / 수학, 철수 / 과학
		* 복합 키
 		- 여러 개의 속성을 묶어서 하나의 기본키로 사용하는 것
 		- 여러 컬럼의 값을 조합해서 겹치는 값이 없으면 된다.

	3. 3차 정규화 : 2 정규화를 만족하면서 이행함수 종속을 제거하는 정규화 과정
		- 기본키가 아닌 다른 컬럼이 다른 일반 컬럼을 결정하면 분리한다.
		- **이행함수 : X,Y,Z 컬럼이 X -> Y, Y -> Z의 종속관계가 있을 때, X -> Z가 성립하는 관계
		- 1(반 번호) / 철수 / 95점 / A 일때 1번 학생의 점수가 95점인 것과 A를 맞았다는 사실을 알 수 있지만, 사실 95점이라 A가 되었다는 더 밀접한 관계가 있다.
		- 이럴 때 95점 -> A라는 관계가 생기므로 분리
		- 1 / 철수 / 95점  //  95점 / A

	- 정규화를 통해서 테이블을 너무 많이 쪼개개 되면 조회를 할 때 성능이 떨어지게 된다.--
	- 이런 경우에는 역정규화를 하기도 한다.
	- 테이블을 만들기 전에 모델링을 잘 하는 것이 매우 중요하다.
