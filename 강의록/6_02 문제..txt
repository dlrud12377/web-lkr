[문제 3] 
다음은 공유 풀(Shared Pool)과 데이터베이스 버퍼 캐시(Data Buffer Cache)에 대한 설명입니다. 대량의 회원을 조회하는 동일한 SQL문이 반복해서 실행될 때, 두 메모리 영역이 SQL 처리 흐름(구문 분석, 실행, 추출) 단계에서 각각 성능 최적화에 어떻게 기여하는지 메커니즘을 비교하여 서술하시오.

공유 풀 : SQL문을 임시로 보관하는 공간으로써, 공유 풀에 저장이 되어 있는 SQL문은 구문 분석을 처음부터 다시 하지 않기 때문에, 그만큼 처리 속도가 빨라져 성능이 높아진다. 해당 상황에서는 동일한 SQL문이 반복해서 실행된다고 했으므로, 임시 보관 공간에서 SQL문이 계속 실행되어 성능 개선에 긍정적인 영향을 준다.

데이터베이스 버퍼 캐시 : 디스크에서 한 번 읽어온 테이블의 데이터를 임시로 올려두는 공간으로써, 버퍼 캐시에 있는 정보는 로딩을 다시 하지 않고 바로 사용할 수 있어 처리속도가 빨라져 성능이 높아진다. 해당 상황에서는 대량의 회원을 조회한다고 했으므로, 동일 데이터 조회로 인해 추가 로딩이 필요없이 버퍼캐시의 데이터를 계속 사용하여 성능 개선에 긍정적인 영향을 준다.

[문제 4] 
APM 리소스 모니터링 화면에서는 CPU 20%, 메모리 40%로 매우 정상적인 수치를 보이고 있으나, 실제 사용자는 "주문 완료 화면이 넘어가는 데 8초 이상 걸린다"며 불편을 겪고 있습니다. 이 현상이 발생할 수 있는 원인을 엔드투엔드(E2E) 모니터링 관점에서 분석하고, 성능 개선을 위해 개발자가 확인해야 할 내부 유틸리티 2가지를 제시하시오.

1. 
사용자
 ↓
주문 서버
 ↓
결제 서버
 ↓
알림 서버
 ↓
DB

E2E 관점에서 볼 때 외부 결제 API 호출 응답 지연, 문자 발송 서버의 지연, 혹은 특정 SQL의 락(LOCK)이나 비효율적인 실행 계획으로 인해 내부 프로세스가 대기 상태에 빠졌을 가능성이 높다.
