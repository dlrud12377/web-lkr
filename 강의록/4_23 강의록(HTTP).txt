 통신은 요청 < - > 응답
 요청(request)를 하는 쪽을 클라이언트(Client)라고 한다.
 응답(response)를 하는 쪽을 서버(Server)라고 한다.

http는 한 번 연결을 하고 나면 기억을 하지 않는다.
1. 클라이언트가 요청을 보냄
2. 서버가 응답을 보냄
3. 연결 종료(끝)

서버 입장에서는 "이 사용자가 방금 전에 뭘 했는지를 모른다."

로그인 요청 -> 성공 후 다음 페이지를 받아야 하는데 서버는 다시 인증을 요구
로그인이 유지가 안됨
로그인한 사람의 장바구니도 유지가 안됨
사용자도 구분이 안되게 됨
이러면 문제가 크게 발생함

-> 상태를 기억하기 위해서는 별도의 기술을 활용해야 함

1. 쿠키
 - 브라우저에 저장되는 데이터
서버 -> 쿠키를 발급
브라우저 -> 요청할 때마다 쿠키를 같이 자동으로 전송

2. 세션(session)
- 서버와 사용자 상태를 기억
java에 session 클래스가 있다.
세션 객체를 만들어서 사용자 상태를 저장한다.

3. 토큰(jwt)
 - 요즘 가장 많이 사용하는 방식
 - 로그인 성공 -> 토큰 지급
 - 클라이언트가 저장
 - 요청 시 토큰을 같이 보냄

MSA(Microservice Architecture)
 - 분산시스템을 구성하기 위해 하나의 큰 어플리케이션을 여러 개의 작은 서비스로 나눠서 개발하고 운영하는 구조
 - 각각의 서비스는 독립적으로 실행된다.
 - 서비스 끼리는 네트워크로 통신(HTTP 등)
 - 배포도 각각 따로 가능함

분산 시스템 SW

시스템
- 여러 요소가 모여 하나의 기능을 수행하는 구조

분산
- 한 곳에 몰아두지 않고 여러 곳에 나누는 것

SW
- 그 구조가 실제로 동작하도록 만드는 소프트웨어

- 따라서 분산 시스템 소프트웨어는 여러 컴퓨터에 기능을 나누어 배치하고, 이들이 서로 통신하면서 하나의 시스템처럼 동작하게 하는 소프트웨어

왜 분산 시스템 SW가 필요할까?
- 한 대의 서버로도 프로그램은 만들 수 있다.
- 하지만 사용자가 많아지고, 기능이 많아지고, 장애에 강해야 하면 한 대만으로는 한계가 생긴다
	- 쇼핑몰에 사용자가 갑자기 10만명이 몰리면, 한 서버가 감당하기 어렵다.

따라서

서버 1: 로그인
서버 2: 상품 목록
서버 3: 결제
서버 4: 리뷰

이런 식으로 서버를 나누어 사용자를 분할함

 - 정리
	(1). 한 대의 서버가 있으면 그 서버가 죽는 순간 서비스 전체가 멈춘다
	(2). 하지만 위의 방식대로 여러 서버로 나누면 일부 서버가 고장나도 서비스가 완전히 멈추지 않도록 설계할 수 있다.

ex. MYSQL, ORACLE

분산환경에서는 데이터베이스도 하나만 쓰지 않고 나누거나 복제하기도 한다.

3. 로드 밸런서
 - 들어오는 요청을 여러 서버에 나누어주는 장치 또는 소프트웨어

단점

 - 데이터베이스를 나누다 보면 데이터가 맞지 않을 수도 있다.

EAI / ESB
- 서로 다른 성격의 시스템을 연결해주는 2가지의 방식

회사에서는 프로그램을 하나만 쓰지 않음
홈페이지 - 주문
창고 시스템 - 재고 관리
회계 시스템 - 매출 계산
배송 시스템 - 배송 상태 관리

 -> 이 시스템들이 서로 연결되지 않으면 사람이 직접 옮겨 적거나, 파일을 수작업으로 옮겨야 함
 -> 따라서 EAI와 ESB 같은 구조가 필요함

 < EAI (Enterprise Application Integration) >
 - 회사 안의 여러 프로그램들을 서로 연결해서 하나처럼 동작하게 만드는 방식
 - 회사 중앙에 연결 담당 센터를 하나 두고 모든 부서가 그 센터를 통해 소통하는 구조

 1. 구조
	- 허브 앤 스포크(Hub and Spoke)
	- Hub : 중심
	- Spoke : 자전거 바퀴 살처럼 바깥으로 연결된 구조
	-> 즉 중앙을 기준으로 모든 부서가 센터를 통해 소통하는 EAI를 잘 설명할 수 있는 모양

< ESB (Enterprise Service Bus) >
 - EAI가 중앙 허브 중심이라면 ESB는 공통 통신 통로(버스)를 만들어서 각 시스템이 버스를 이용해 유연하게 통신하는 방식

 1. 특징
	(1). 표준 기반 통신
	 - 서로 다른 시스템들이 같은 방식으로 통신할 수 있게 한다.

	(2). 느슨한 결합
	 - 시스템끼리 아주 강하게 묶이지 않게 만든다.

	(3). 메시지 중심 구조
	 - 데이터를 메시지 형태로 주고받는다.

	(4). 라우팅 기능
	 - 어떤 메시지를 어떤 시스템으로 보낼지 결정

	(5). 변환 기능
	 - 데이터 형식을 바꿔준다.

	(6). 확장성이 좋다.
	 - 서비스가 늘어나도 비교적 유연하게 붙일 수 있다.

 < 실시간 데이터 처리 >
 - 여러 개의 데이터를 실시간으로 분석해서 의미있는 이벤트(상황)를 만들어 내는 기술

 < 이벤트 >
 - 시스템에서 발생하는 하나의 데이터 또는 상황(사건)
 	- 로그인 발생
 	- 상품 주문 발생
 	- 센서 값 변화
 	- 결제 시도
 	- 버튼 클릭

여기서 CEP(Complex Event Processing)는 무엇을 하는가
 - 여러 이벤트를 조합해서 "의미있는 상황"을 판단한다.

	예시1)
	10초 안에 서울에서 카드로 결제
	10초 안에 부산에서 카드로 결제
	 -> 물리적으로 불가능 -> 카드의 부정사용 의심(판단)

	예시2)
	사용자가 상품을 클릭
	장바구니 담기
	10초 이내
 	결제
	"구매패턴(의미있는 상황) 발생" -> 마케팅 분석(판단)에 활용 가능

< 이벤트 발생 시 행동패턴 >

1. 이벤트 발생
ㄴ 사용자의 행동
ㄴ 시스템 로그
ㄴ 센서 데이터

2. 이벤트 수집

3. CEP엔진 분석
 - 이벤트 패턴 분석
 - 조건 검사
 - 시간 기반 처리

4. 결과 이벤트 생성
 - 경고 발생
 - 알림 전송
 - 자동 처리 실행

TP모니터
 - 트랜젝션(여러 사용자의 요청)을 안정적으로 처리하고 관리해주는 미들웨어

TP모니터가 필요한 이유
 - 서버에 직접 요청을 보내면
	1. 동시에 너무 많은 요청이 발생
	2. 데이터가 충돌
	3. 일부만 처리되는 문제 발생
	4. 서버 과부하
 
 -> TP모니터가 중간에서 요청을 관리, 순서를 조정, 트랜젝션을 보장, 오류를 복구한다.

IT자원
 - CPU가 하는 연산
 - 메모리
 - 디스크에 저장공간
 - 네트워크
 - 서버
 -> 컴퓨터가 일할 때 사용하는 모든 것을 의미함

이러한 IT자원을 관리하는 미들웨어가 필요한 이유
 - 서버 하나에 작업이 몰릴 수 있다.
 - CPU 100%를 사용하면 서버가 다운됨
 - 메모리가 부족하면 프로그램이 종료됨
 - 특정 서버만 과부하가 걸릴 수도 있음
 -> 자원관리 미들웨어를 사용하게 되면 작업을 여러 서버에 분산하고, 자원 사용량을 모니터링하여 자동조정할 수 있다.

핵심 역할
1. 자원 할당
 - 어떤 작업에 CPU, 메모리를 얼마나 줄 지 결정함

2. 자원 분배
 - 여러 서버에 작업을 나눈다

3. 모니터링
 - CPU, 메모리, 네트워크 상태 확인

4. 부하를 분산
 - 한쪽에 몰리지 않게 조절

5. 자동 확장
 - 트래픽이 많으면 서버 추가
 - 트래픽이 적으면 서버를 줄임

IT자원을 관리하는 미들웨어의 예시

1. Docker(docker : 항만 관리자 : 무역선 컨테이너를 관리)
image : 설계도(어떤 내용을 포함할건지)
 - 어플리케이션을 컨테이너로 실행 -> 실행 환경(OS나 관련된 내용들)을 컨테이너 내에 함께 셋업할 수 있어서 환경의 일관성을 챙길 수 있음(이 컴퓨터에서는 되고 이 컴퓨터에서는 안되는 문제를 해결)
 - 자원을 격리해서 사용

2. kubernetes
 - 컨테이너를 여러 서버에 배치(컨테이너당 docker가 하나씩 붙고, 그걸 여러 서버를 통해 통합 관리)
 - 자동으로 스케일링
 - 장애 발생 시 재배치

단점
 - 설정과 운영 난이도가 높음

전자정부 표준프레임워크의 구성
로그인, 세션 관리와 같은 시스템 구축시 공통적으로 개발하는 부분을 공통 컴퍼넌트로 제공하고 개발에 필요한 오픈소스 기반의 개발 도구, 실행 환경, 관리 환경, 운영 환경 등을 표준 프레임워크로 제공한다.

유지 보수 쉬움
공공 프로젝트에서는 필수 수준

 1. 특징
   - 어플리케이션 성능 관리 도구
   - Java 기반 웹 서버 성능을 실시간으로 분석하는 도구
   - 현재는 오픈소스로 공개되어 다양한 기업과 개발자들이 사용하고 있다.

 2. 주요 기능
   (1). 서버 상태 모니터링
	- cpu 사용량
	- 메모리 사용량
	- 현재 요청 상태

   (2). SQL 쿼리 분석
	- 느린 쿼리(Slow Query) 탐지
	 -> DB가 느린 원인 찾기 가능
		* DB(DataBase) : 데이터들의 묶음(회원, 제품 등등)
		* DBMS(DataBase Management System) : 데이터베이스 관리 시스템
		* SQL(Structured Query Language) : 데이터베이스에 데이터를 저장, 조회, 수정, 삭제하기 위해 사용하는 언어

   (3). 트랜젝션 추적
	- 사용자 요청 -> 응답까지 시간 분석
	-> 어디서 느려지는지 확인

   (4). 웹 어플리케이션 성능 모니터링


 < 데이터베이스 기초 활용하기 >
 
 1. 데이터(Data)란?
  - 객관적인 사실이나 값을 나타내는 것으로 숫자, 문자, 이미지, 비디오 등과 같은 형태로 나타낸다.
 - 이러한 데이터들은 특정 의미를 부여받아 정보가 되기도 하고 더 나아가 지식으로 발전할수도 있다.

 2. 데이터베이스
	- 파일을 저장하고 관리하는 특수한 형태로 데이터를 공용으로 활용하기 위해 통합하여 저장한 운영 데이터의 집합

 3. 데이터베이스의 특징
	(1). 실시간 접근성
		- 요청받은 데이터는 실시간으로 처리되고 결과를 반환해야 한다.
	
	(2). 계속적 변화
		- 저장된 데이터는 입력, 수정, 삭제에 의해 지속적으로 변화한다.

	(3). 동시 공용
		- 서로 다른 목적의 SW 및 사용자에 의해 동시 공용 가능

	(4). 내용에 의한 참조
		- 데이터 참조는 데이터의 주소가 아닌 저장된 값에 의해 처리된다.

 DBMS(DataBase Management System) : 데이터베이스 관리 시스템
 - 다수의 응용 소프트웨어 및 사용자가 데이터베이스에 접근하여 저장되어 있는 데이터베이스를 필요에 따라 사용할 수 있도록 관리해주는 시스템

데이터베이스 관리 시스템의 기능
	(1). 동시성 제어
		- 다수 트랜젝션의 동시 처리로부터 데이터 무결성 확보를 위한 제어 수행
		ㄴ 여러 사용자가 같은 데이터에 동시에 접근할 때
		 ex. A가 같은 계좌에서 5만원 출금
		     B가 같은 계좌에서 3만원 출금
			**트랜젝션 : 하나의 SQL 명령문을 의미함

	(2). 회복 관리
		- 시스템 오류 및 장애로 인한 데이터 손실 및 결함의 대응

	(3). 성능
		- 데이터 처리 속도 확보를 위한 실행 계획의 최적화

	(4). 보안 관리
		- 비인가 사용의 접근 제어 및 중요한 정보의 암호화

 데이터베이스 관리 시스템의 유형
	(1). 계층형
		- 트리 구조로 데이터 저장(부모-자식 관계가 형성)(가계도같은 느낌. 대신 부모는 하나로 침)
		- 자식은 하나의 부모만 가진다.
		- 데이터 접근속도 빠름, 구조는 단순함
		- 구조 변경이 어려움, 유연성 부족, 관계가 복잡해지면 관리가 어려움

	(2). 네트워크형
		- 그래프 구조, 데이터간 다대다 관계 가능
		- 데이터 노드와 관계를 링크로 연결
		- 복잡한 관계표현 가능, 데이터 
		- ?

	(3). 관계형
		- 테이블 형태로 데이터를 저장
		- 행과 열로 구성이 되어 있다.
		- SQL 사용, 스키마 기반(데이터를 어떻게 저장할지 미리 정의해둔 구조), 정규화 지원
		- 직관적, 표준 SQL 지원, 데이터 무결성 보안 우수
		- 단점 : 대규모 데이터 처리시 성능 저하 가능

		종류 : Oracle, MySQL, ?,MSSQL
 

	(4). 객체지향형
		- 객체 단위로 데이터 저장, 속성과 메서드 포함
		- 객체지향 언어와 연동 용이, 상속 다형성 지원
		- 복잡한 데이터 구조 직접 표현 가능, 재사용성 높음
		- 단점 : 표준화 부족, 학습 곡선이 높음

	(5). 객체관계형
		 - 관계형 데이터베이스에 객체지향 개념을 추가
		 - 대용량 멀티미디어 처리 가능
		 - 기존 RDBMS 장점을 유지, 복잡한 데이터 처리 가능
		 - 구현이 복잡, 성능 최적화 어려움


DBMS별 특징
관계형
- MySQL : 널리 사용됨, 오픈소스, 안정성 높음
- MariaDB : MySQL 포크 버전, 오픈소스, 성능 개선
- PostgreSQL : 고급 SQL 기능, ACID 준수, JSON 지원, 확장성 높음
 * ACID
 	- Atomicity(원자성 : 트랜젝션이 여러개일 때 전부 성공하거나, 전부 실패해야 함 - 작업이 실패하면 아예 롤백)
	 - Consistency(일관성 : 트랜젝션 전후에 데이터 규칙이 유지되어야 한다. - 트랜젝션이 규칙을 위반하면 롤백)
		ex. 계좌 잔액은 0원 이상이어야 한다.
 	- Isolation(격리성 : 여러 트랜젝션이 서로 간섭하지 않아야 한다.)
		ex. A가 데이터를 수정중일 때 B가 그 데이터의 상태를 중간에 확인할 수 없다.
 	- Durability(지속성 : 성공한 작업은 절대 사라지면 안된다.)
		ex. 결제 기록이 사라지면 안됨

 - Oracle : 대규모 기업 환경에 강함. 보안, 백업, 복구 기능 강력함
 - SQLite : 서버 없이 사용 가능, 경량, 임베디드DB
  **임베디드 데이터베이스(Embedded Database) : 애플리케이션 내부에 라이브러리 형태로 포함되어, 별도의 서버 프로세스 없이 동작하는 경량 고속 DBMS

NoSQL
 - Redis : 초고속 처리, 캐싱, 세션 관리에 최적화

< 트랜젝션 >
 - 데이터베이스 관리시스템에서 저장된 데이터의 상태를 바꾸기 위해 수행하는 작업의 논리적 단위
	** 논리적 단위 : 여러 개의 작업을 하나로 묶어서 '전부 성공' 또는 '전부 실패'로 구분하는 것을 의미한다.
			즉 원자성을 발휘할 수 있는 논리 단위(기본적으로 ACID를 준수해야 하기 때문에)
