	1. 논리 데이터 저장소 확인하기
		ㄴ엔티티, 속성, 관계
		ㄴ정규화

	2. 물리 데이터 저장소 설계하기
		ㄴ반정규화 : 테이블이 너무 나눠져 있어서 JOIN을 너무 많이하면 조회 성능이 떨어짐. 이 때 테이블을 합치는 작업
	
			(1). 중복 테이블 추가
			 - 집계 테이블 추가
			 - 상태 컬럼을 담고 있는 테이블을 생성
			 - 특정 부분만을 포함하는 테이블 추가

			(2). 테이블 조합
			 - 항상 같이 사용되는 두 개 이상의 테이블을 하나로 합치는 것

			(3). 테이블 분할
			 - 수직분할 : 컬럼별 사용 빈도의 차이가 많은 경우 자주 사용되는 컬럼과 그렇지 않은 컬럼으로 분류하여 테이블 분할
			 - 수평분할 : 특정 범위별 사용 빈도 차이가 많은 경우 해당 범위별로 테이블을 분할하는 방법

			(4). 테이블 제거
			 - 테이블 재정의나 컬럼의 중복화로 더 이상 사용되지 않는 테이블이 발생하면 (백업 후) 삭제하기

			(5). 컬럼 중복
			 - 필요한 해당 테이블이나 컬럼을 중복하여 추가
			 - 다른 테이블에 있는 컬럼을 현재 테이블에도 추가로 저장하는 것

	3. 물리 데이터 모델링 하기
	 - 논리 모델링을 통해 얻은 내용을 데이터베이스에 사용할 수 있는 물리 데이터 모델로 변환
		엔티티 -> 테이블로 변환
		ㄴ 일반적으로 테이블과 엔티티 명칭은 동일하게 하는 것을 권고

		속성 -> 컬럼으로 변환
		ㄴ 속성의 명칭과 반드시 일치할 필요는 없으나, 개발자와 사용자 간의 의사소통을 위하여 가능한 표준화된 언어를 사용하도록 한다.
		ㄴ SQL 예약어 사용은 피해야 한다.
		ㄴ SQL 문장의 가독성을 높이기 위해 컬럼명칭은 가능한 짧은 것이 좋다.

		UID -> 기본키(PK)로 변환

		관계 -> 외래키(FK)로 변환
		ㄴ 외래키로 설정된 컬럼의 이름도 보통은 기본키쪽의 이름을 그대로 사용
		ㄴ 다른 의미를 가지면 바꿔도 된다.

		컬럼 타입 및 길이를 정의
		ㄴ 내가 넣으려는 데이터의 크기를 파악해서 컬럼의 길이를 지정

		반정규화 적용 여부를 검토

	4. 물리 데이터 저장소 구성
	
		1. 테이블 제약조건
		 - 기본키와 외래키로 관계를 맺고 있는 테이블에서의 제약조건(연결관계)

		회원
		user_id (PK)

		주문
		user_id (FK) -> 정보가 연결되어있어서 회원 테이블을 지울 때 주문테이블에도 제약이 걸림

			(1). 삭제할 때
			 - 참조된 기본키의 값이 삭제될 경우 어떻게 처리할지 정하는 규칙
				-> 고객이 삭제되면, 그 고객의 주문 데이터는 어떻게 할 것인가

			* CASCADE(의미 : 연쇄, 폭포..)
			 - 부모 테이블의 데이터가 삭제되면, 그 데이터를 참조하고 있던 자식 테이블의 데이터도 함께 삭제되는 방식
				EX. 
				FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
				ON DELETE CASCADE

			* RESTRICTED
			 - 자식 테이블에서 사용 중인 값이 있으면 부모 데이터를 삭제하지 못하게 막는 방식
				EX. 
				FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
				ON DELETE RESTRICT; -- 쓸 때는 RESTRICTED X / RESTRICT O

			* Nullify
			 - 부모 데이터가 삭제되면, 자식 테이블의 외래키 값을 NULL로 바꾸기
			 - 자식테이블의 외래키 커럼이 반드시 NULL을 허용해야 한다(NOT NULL이면 안된다)
				EX. 
				FOREIGN KEY (customer_id) REFERENCES customer(customer_id)
				ON DELETE SET Null;

			(2). 수정할 때(DELETE -> UPDATE)
		
			* CASCADE
			 - 기본키 내용이 수정되면 참조하는 외래키 값도 같이 수정되는 것
			(ON UPDATE CASCADE)

			* RESTRICTED
			 - 외래키로 참조되고 있으면 기본키의 값을 수정하지 못하도록 막음
			(ON UPDATE RESTRICT)

			* Nullify
			 - 부모 테이블의 기본키 값이 수정되면, 자식 테이블의 외래키 값을 NULL로 바꾸는 것
			(ON UPDATE SET NULL)


		2. 인덱스 설계
		 - 데이터를 빠르게 찾기 위해 만드는 검색용 목차

		 - 인덱스 적용 기준
		컬럼의 분포도가 10 ~ 15% 이내인 경우
		분포도 : 해당 컬럼의 값이 얼마나 다양하게 나뉘어 있는지 의미
		분포도 = (1 / 컬럼의 도메인 개수) X 100

		ex. 남녀 -> (1/2) X 100 = 50%
		인덱스 효과가 크지 않음(분포도가 크다는 것은 저 기준으로 원하는 정보가 많이 구체화되지 않음)

		주민등록번호 10000개 -> (1/10000) X 100 = 0.01%
		인덱스 효율이 매우 좋은 컬럼
		
		* 분포도에 따른 인덱스 효율
		10% 이하 : 효율이 좋다.
		10~15% : 일반적으로 인덱스를 사용할 수 있다.
		15% 이상 : 인덱스 효율이 좋지 않다.

		* 분포도 범위가 이상이더라도 부분 처리를 목적으로 하는 경우

			(1). 
			예시 데이터
			주문상태	건수
			완료		90000
			배송중	8000
			취소		2000

			데이터량은 완료, 배송중이 더 많지만, 실제 업무에서 자주 조회하는 데이터가 '취소' 2000건이라면
			전체의 2%만 조회하게 된다.
			 - 이런 경우 부분 처리를 목적으로 인덱스를 사용할 수 있다.
			 - 단순히 값의 종류만 보지 말고 실제 조회 조건에서 몇건이 조회되는지 봐야함

			(2). 조회 및 출력
			 - 입출력 표나 화면 설계서에서 자주 검색 조건으로 사용되는 컬럼인 경우

			예시 데이터
			주문
			주문번호
			회원 ID
			주문일자
			주문상태

			 - 누가 언제 주문을 하는지 조회를 많이 한다면 회원ID랑 주문일자에 인덱스를 고려할 수도 있다.
			?
			 - 기본키랑 UNIQUE 제약조건은 인덱스를 자동으로 생성한다.

		* 인덱스 컬럼의 선정
		 - 분포도가 좋은 컬럼은 단독 인덱스로 생성한다.
		분포도가 좋다는 것은 검색 결과가 적게 나오는 컬럼이라는 뜻

		예시 데이터
		회원번호		이메일
		1			a@test.com
		2			b@test.com
		3			c@test.com
		4			d@test.com
		5			e@test.com

		인덱스는 보통 특정 컬럼에 조건을 걸 때 사용이 된다.

		select *
		from user
		where email = 'c@test.com';

		CREATE INDEX idx_user
		ON users(email);

		결합 인덱스를 사용하는 경우
		 - 조건이 여러 개 걸릴 때

		select *
		from orders
		where member_id = 10
		and order_date >= '2026-01-01';

		CREATE INDEX idx_member_id_order_date
		ON orders(member_id, order_date);

		결합 인덱스는 컬럼 순서가 중요하다
		
		수정이 빈번하지 않은 컬럼을 선정한다.
		 - 인덱스는 조회를 빠르게 해주지만, 삽입, 수정, 삭제 작업에는 부담이 된다.
		 - 인덱스로 선정한 컬럼의 정리 내용을 따로 저장을 하기 때문에 테이블 데이터가 바뀔 때 인덱스도 같이 바뀌어야 한다.

		* 설계 시 고려사항

		새 인덱스가 기존 액세스 경로에 영향을 줄 수 있다.
		 - 액세스 경로 : DBMS가 데이터를 찾기 위해 선택한 이동 방법
		
		* 대표적인 액세스 경로 종류
		
			1. Full Table Scan(전체 테이블 검색)
			 - DB가 처음부터 끝까지 전부 읽는다.

			2. Index Scan(인덱스 검색)
			 - 인덱스를 사용해서 필요한 위치만 바로 찾는다.
			 - 인덱스를 지나치게 많이 만들면 오버헤드가 된다.
		
			* 오버헤드(Overhead) : 빠르게 찾기 위해 만들어둔 목차가 너무 많아서, 오히려 관리가 힘들어지는 것
			 - 인덱스가 많으면 조회는 빨라질 수 있지만, 데이터 변경 작업은 느려진다.

		* 인덱스는 추가 저장공간이 필요하다.
		 - 인덱스는 테이블과 별도로 저장되는 검색 구조이다.
		 - 인덱스를 만들면 저장 공간을 추가로 사용한다.

		* 넓은 범위를 인덱스로 처리하면 오히려 느릴 수 있다.
		 - 적은 데이터를 빠르게 찾을 때 효과적이다.
		 - 하지만 전체 데이터의 많은 부분을 조회하면 오히려 전체 테이블을 읽는 것이 더 빠를 수 있다.

		* 인덱스와 테이블 데이터의 저장 공간을 적절히 분리한다.
		 - 대규모 DB에서는 테이블 데이터와 인덱스 데이터를 물리적으로 분리해서 저장하기도 한다.

	3. 뷰(View) 설계
	 - SELECT 한 결과를 테이블인 것처럼 저장하는 가상 테이블

	* 뷰가 필요한 이유
	 - 복잡한 SQL을 단순하게 사용할 수 있다.
	 - 특정 컬럼만 보여줄 수 있다.(보안성)
	 - 조건에 맞는 데이터만 보여줄 수 있다.

	* 뷰 속성

		(1). REPLACE
		 : 뷰가 이미 존재하는 경우 기존 뷰를 새 내용으로 다시 생성하는 속성
		CREATE OR REPLACE 뷰 이름 AS (테이블 SELECT문)
		MYSQL & ORACLE 둘 다 됨

		(2). FORCE(강제)
		 : 참조하려는 테이블이 존재하지 않아도 뷰를 생성하는 속성(강제 생성이 가능)

		ORACLE만 됨

		- 뷰를 사용하려고 하면 에러가 발생할 수 있다.

		cf). NOFORCE
		 : 참조하려는 테이블이 무조건 존재해야 뷰를 생성하는 속성(강제 생성 불가)

		ORACLE만 됨

		(3). WITH CHECK OPTION
		 : 뷰의 조건을 만족하는 행만 INSERT, UPDATE할 수 있도록 제한하는 속성
		 - 원본 테이블이 아닌 뷰에다가 INSERT, UPDATE를 하는 것

		(4). WITH READ ONLY
		 - 뷰를 조회 전용으로 만드는 속성이다.

			** (4), (5)의 WITH문 사용법
			CREATE VIEW 뷰이름 AS
			SELECT ~
			WITH (CHECK OPTION / READ ONLY);

	* 뷰 설계 시 고려사항
	 - 뷰는 결국 테이블을 조회한다.
		 - 실제 데이터를 저장하지 않는다.
		 - 뷰는 내부적으로 SELECT문을 실행해서 결과를 보여준다.
		 - 그래서 뷰를 사용한다고 해서 무조건 빨라지는건 아니다.
		 - 오히려 뷰 안의 SQL이 복잡하면 성능 문제가 생길 수 있다.

	 - 복잡한 뷰는 성능이 느려질 수 있다.

	 - 뷰 안의 SELECT문의 조건도 인덱스를 고려해야 한다.

	
	4. 파티션
	 - 하나의 큰 테이블을 내부적으로 여러 조각으로 나누어 저장하는 기술
	 - 겉으로는 하나의 테이블로 보여진다.

	 * 왜 파티션이 필요한가?
	 - 대용량 데이터를 여러 영역으로 나누어 저장함으로써, 조회시 필요한 데이터만 읽어 성능을 향상시키고, 백업, 복구, 삭제 같은 관리 작업을 효율적으로 수행하기 위해 사용한다.

	 * 인덱스 VS 파티션
		 인덱스
		  - 목적 : 데이터를 빠르게 탐색
		  - 개념 : 데이터 탐색 속도 향상
		 데이터를 정렬된 구조로 저장
		 책의 목차 / 책갈피와 같음	

		 파티션
		  - 목적 : 데이터를 나눠서 관리
		  - 개념 : 읽을 데이터 범위를 축소
		 데이터를 여러 영역으로 분리 저장
		 여러 책의 합본과 같음(사이사이에 표지가 있는)
		 필요한 영역만 읽어서 속도를 향상

	 * 파티션의 종류

		 1. 범위 분할
		  - 특정 컬럼 값의 범위에 따라 데이터를 나누어 저장하는 방법

		  - SQL 작성 방법
		  CREATE TABLE 테이블 명(
 			 컬럼들..
		 )
		  PARTITION BY 파티션방식(컬럼) (
			 파티션 정의
			 PARTITION 이름 VALUES LESS THAN (데이터) -> 파티션 개수만큼 반복
		 )

		 파티션을 만들어 놓고 평소대로 사용하듯이 해도 DB가 알아서 조회

		2024 ~ 2026년의 데이터를 가지고 있을 때
		각 년도별로 파티션을 분할했다면

		2025년 데이터만 조회
		-> 2025년 데이터가 들어있는 파티션만 확인
		-> 2024, 2026년 데이터가 들어있는 파티션은 확인하지 않는다.

		오래된 데이터를 관리하기 쉽다.
		일반적인 구간 삭제
		DELETE FROM orders
		WHERE order_date BETWEEN '2024-01-01' AND '2024-12-31';

		파티션을 이용한 구간 삭제
		ALTER TABLE orders DROP PARTITION p2024(2024년 자료가 있는 파티션 이름);

		주로 사용하는 경우
		주문 데이터
		로그 데이터
		게시글 데이터
		이력 데이터

		2. 해시 분할(Hash Partitioning)
		 - 특정 컬럼 값을 계산(Hash)해서 데이터를 여러 구역에 균등하게 나누어 저장하는 방법
		 - 범위 분할의 경우는 사람이 직접 분할의 기준을 정했으나, 
	
		년도를 기준으로 파티션을 정했을 때

		2023년 -> p2023
		2024년 -> p2024
		2025년 -> p2025
		2026년 -> p2026

		해시분할은 DB가 직접 계산에서 자동으로 분배를 한다.

		데이터 편중 문제
		2024년에는 주문이 많았다. -> p2024 파티션에 너무 많은 데이터가 들어감
		2025년에는 주문이 적다.

		이럴 경우 해시 분할을 사용

		CREATE TABLE users(
			user_id INT,
			name VARCHAR(50)
		)
		PARTITION BY HASH(user_id)
		PARTITIONS 4; -- 나누려는 파티션 개수

		DB는 내부적으로 해시값 %(나머지 나누기) 파티션 개수 방식으로 계산을 한다.
	
		N % 4
		0 : 4, 8, 12, 16......
		1 : 1, 5, 9, 13...
		2 : 2, 6, 10, 14....
		3 : 3, 7, 11, 15....
		-> 균등하게 데이터가 파티션별로 들어감

		* 해시 분할의 장점
		 - 데이터 분산 : 특정 파티션에 데이터가 몰리는 현상을 감소시킴
		 - 저장 균형 : 여러 파티션 크기를 비슷하게 유지
		 - 특정 키 조회 빠름 : ID 기본 조회에 적합
		 - 대용량 처리 : 부하를 여러 파티션으로 분산할 수 있다.

		* 해시 분할의 단점
		 - 범위 조회에 약함 : 날짜 범위 검색 비효율적
		 - 사람이 예측하기 어렵다 : 어느 파티션에 있는지 알기 어렵다
		 - 파티션 개수 변경이 어렵다 : 재분배 작업이 발생할 수 있다

		* 사용처
		 - 회원 테이블
		 - 사용자 정보
		 - 고객 테이블
		 - 게임 사용자 데이터
		 - ID(PK) 기반 조회가 많은 시스템

		3. 조합 분할(Composite Partitioning)
		 - 파티션 기준을 2개 이상 조합해서 데이터를 나누는 방식
		 - 먼저 큰 기준으로 한 번 나누고, 그 안에서 다시 작은 기준으로 한 번 더 나누는 방식

		orders
		ㄴ p2024 (2024년 주문)
		ㄴ p2025 (2025년 주문)
		ㄴ p2026 (2026년 주문) -> 1천만 개

		연도별로 나누어도 p2025안에서는 여전히 데이터가 많다.
		파티션 안에서 파티션을 한 번 더 나눈다.

		1차 분할 : 주문일 기준 연도별 분할
		2차 분할 : 고객번호 기준 해시 분할

		CREATE TABLE orders(
			order_id INT,
			customer_id INT,
			order_date DATE
		)
		PARTITION BY RANGE(YEAR(order_date)) -> 주문일의 연도 기준으로 먼저 나눔
		SUB PARTITION BY HASH(customer_id)
		SUB PARTITIONS 4 -> 각 년도 파티션 안에서 고객번호를 기준으로 다시 4개로 나누기
		(
			PARTITION p2024 VALUES LESS THAN (2025),
			PARTITION p2025 VALUES LESS THAN (2026),
			PARTITION p2026 VALUES LESS THAN (2027)
		);

		1단계 : 년도별
		2025년도
		-> p2025


		2단계 : 고객 번호
		customer_id = 11

		11 % 4 = 3

		p2025의 세번째 서브파티션에 들어가게 된다.

		orders
		ㄴp2025
			ㄴsub3

		조회할 때 어떻게 동작할까?
		 - 연도 조건만 있는 경우
		select	*
		from orders
		where order_date between '2025-01-01' and '2025-12-31';

		2025년 파티션만 찾는다.
		단, p2025내부의 서브파티션은 여러개를 확인할 수 있다.

		select	*
		from orders
		where order_date between '2025-01-01' and '2025-12-31';
		and customer_id = 11;

		p2025 먼저 탐색 후
		고객번호가 들어있는 파티션만 탐색

		* 조합 분할을 사용하는 이유
		 - 대용량 데이터 관리 : 1차 파티션만으로 부족할 때 사용
		 - 조회 범위 축소 : 날짜 조건과 고객 조건을 함께 자주 조회할 때 좋다.
		 - 데이터 분산 : 특정 연도나 월에 데이터가 몰리는 문제를 줄일 수 있다.
		 - 관리 편의성 : 연도별 삭제, 백업 같은 작업을 하면서 내부 분산도 가능하다.

		* 조합 분할을 사용하면 좋은 상황
		 - 주문 테이블 1차 : 주문일 / 2차 : 고객번호
		 - 로그 테이블 1차 : 생성일 / 2차 : 사용자 ID
		 - 결제 테이블 1차 : 결제일 / 2차 : 회원 ID
		 - 게시글 이력 테이블 1차 : 작성일 / 2차 : 작성자 ID

		* 조합 분할이 장점을 가지는 기준
		 - 단순 CRUD 중심일 때
		 - 날짜 조건만으로 충분할 때
		 - 파티션 관리 경험이 부족할 때
		 - 조회 조건이 파티션 기준과 맞지 않을 때

	* 파티션 장점
	 - 읽어야 하는 데이터 범위를 줄여서 성능을 향상
	 - 전체 데이터 훼손 가능성 감소 및 데이터 가용성 향상
	 - 각 분할 영역을 독립적으로 백업하고 복구가 가능하다.
	 - 디스크 스트리핑으로 I/O 성능 향상

	** 디스크 스트리핑(disk striping) : 데이터를 여러 디스크에 나눠서 동시에 저장하거나 읽는 방식

	* 파티셔닝 순서
	 - 파티션 종류 결정(범위, 분할, 조합)
		ㄴ 데이터를 어떤 방식으로 나눌지 결정
			- 범위 분할 : 값의 범위로 나눈다
			- 해시 분할 : 해시 계산 결과로 나눈다
			- 조합 분할 : 두 가지 방식을 함께 사용
	 - 파티션을 할 키를 설정
		ㄴ 데이터를 나눌 기준이 되는 컬럼을 설정
		ㄴ 좋은 파티션 키는 데이터를 어느 정도 고르게 나누거나 자주 조회되는 범위를 효과적으로 줄여줄 수 있어야 한다.
		ㄴ 이력 데이터는 생성주기 또는 소멸주기와 맞춘다.
		ㄴ 전체 테이블에서 오래된 데이터를 한 건씩 삭제하는 것보다 파티션 단위로 관리하는 것이 효율적이다.
	 - 파티션의 개수를 설정
		- 데이터의 양 : 한 파티션이 너무 커지지 않게 한다
		- 조회 패턴 : 자주 조회하는 단위와 맞춘다.
		- 보관 정책 : 삭제, 백업 단위와 맞춤
		- 관리 편의성 : 너무 많은 파티션은 피한다.
		- I/O 분산 : 특정 파티션에 너무 몰리지 않게 한다.
	
	5. 클러스터 설계
	 - 자주 조회되는 데이터를 디스크의 가까운 위치에 모아 저장해서 조회 속도를 높이는 물리적 저장방법이다.
	
	 - 일반 저장 방식 vs 클러스터 저장 방식
		 - 일반 저장 방식 : 책이 아무 책장이나 흩어져 있는 상태(규칙 X)
		 - 클러스터 저장 방식 : 자주 같이 보는 책들끼리 같은 책장이나 가까운 칸에 모아둠(규칙 O, 효율성 O)
			-> 그렇기 때문에 클러스터 방식이 조회할 때는 빠르다
			but 책을 새로 넣거나(INSERT) 위치를 바꾸거나(UPDATE) 삭제할 때는(DELETE) 정리 비용이 더 소모된다.

	 - 파티션 vs 클러스터
		 - 파티션 : 저장 공간을 나눈다.
		 - 클러스터 : 관련 데이터를 가까이 저장한다.

		ex. 테이블 만들기
		customer
		customer_id	name
		1			김철수
		2			박민수
		3			이영희
		이렇게 테이블이 저장되어있다고 가정하면
		테이블도 결국에는 컴퓨터 저장장치 어딘가에 저장이 된다.

		order
		order_id		customer_id
		101			1
		102			1

		JOIN을 수행
		SELECT *
		FROM customer c
		JOIN orders o
		ON c.customer_id = o.customer_id;

		DB가 JOIN을 하려면 저장장치 내부를 계속 이동을 해야 한다.
		멀리 떨어진 위치를 읽으려고 하면 속도가 떨어질 수 있다.
		-> 그래서 같이 자주 사용되거나 FK로 연관되어있는 내용들끼리
		물리적으로 가깝게 배치하는 것을 의미한다.

	 * 클러스터 설계 방법
		
		1. 클러스터 만들기
		Oracle 기준
		CREATE CLUSTER customer_order_cluster(
			customer_id NUMBER
		)

		-> customer_id가 같은 데이터끼리 같은 공간에 저장할 창고를 만들어라

		2. 클러스터 인덱스를 만든다
		CREATE INDEX idx_customer_order_cluster
		ON CLUSTER customer_order_cluster;

		3. 클러스터를 사용하는 테이블 생성
		CREATE TABLE customer(
			customer_id NUMBER PRIMARY KEY,
			customer_name VARCHAR2(50) NOT NULL
		)
		CLUSTER customer_order_cluster(customer_id);
		
		CREATE TABLE orders(
			order_id,
			customer_id,
			...
		)
		CLUSTER customer_order_cluster(customer_id);

		-> 이런 식으로 만들면 같은 customer_id를 가진 데이터가 물리적으로 가까운 위치에 저장될 수 있다.

		MySQL
		 - Oracle처럼 CREATE CLUSTER를 통해 클러스터를 생성하지는 않는다.
		 - InnoDB 테이블의 PRIMARY KEY가 자동으로 클러스터형 인덱스가 된다.
		 - MySQL 공식 문서에서도 InnoDB는 테이블에 PRIMARY KEY를 정의하면 그것을 CLUSTERED INDEX로 사용한다고 적혀 있다.

		** InnoDB
		 - MySQL에서 테이블 데이터를 저장하고 관리하는 저장 엔진

		결론 : MySQL에서는 PK를 만들면 곧 클러스터가 된다.

	* 클러스터 적용 기준
	 - 분포도가 넓을수록 유리한 기법
		 - 인덱스 : 조건으로 조회했을 때의 데이터가 적을수록 유리
		 - 반대로 조회범위가 너무 넓으면 인덱스를 타도 많은 행을 계속 찾아가야 해서 오히려 부담이 된다.

		EX.
		SELECT *
		FROM orders
		WHERE order_date BETWEEN '2026-01-01' AND '2026-03-31'

		 - 위 상황에서 3개월치 주문 데이터가 매우 많다면 인덱스로 하나하나 찾아가는 비용이 커진다.
		 -> 이런 경우 관련 데이터를 물리적으로 가까이 모아두는 클러스터가 도움이 된다.

	* 클러스터의 저장 방식
		 - 클러스터는 액세스 기법이 아니라 물리적 저장방법이다.

		ex.
		SELECT *
		FROM ORDERS
		WHERE customer_id = 10;

		 - 클러스터는 sql문법에서 직접 "클러스터로 검색해라"라고 지시하는 개념이 아니다.
		 - 클러스터는 미리 데이터를 저장할 때 관련있는 데이터를 가깝게 저장한다.

	 * 클러스터의 장점 및 특징
		 - 분포도가 넓은 테이블은 저장 공간 절약이 가능하다 ( 분포도가 넓다? 컬럼 개수가 많을수록 분포도가 떨어짐)
			 - 클러스터링을 잘하면 같은 기준의 데이터가 모여 저장된다.
			customer_id = 1인 주문들
			customer_id = 2인 주문들
			customer_id = 3인 주문들
			 - 위와 같은 키 값을 가진 데이터들이 모이면, 반복되는 키 관리나 블록 접근 측면에서 저장 효율이 좋아질 수 있다.
			 - 단, 무조건 저장 공간이 줄어드는 것은 아니다.
			 - 설계가 잘못되면 오히려 공간 낭비가 생길 수 있다.

				-> 작은 테이블 vs 큰 테이블

				작은 테이블
				-> 그냥 전체 조회해도 빠름
				-> 클러스터 설계 효과가 작다

				큰 테이블
				-> 여러 블록에 데이터가 흩어질 수 있다.
				-> 클러스터 설계효과가 커질 수 있다.

			 - 결론 : 클러스터는 데이터가 충분히 많고, 조회 패턴이 반복적으로 발생할 때 의미가 있다.

		 - 인덱스를 사용한 처리가 부담되는 넓은(낮은) 분포도에 활용한다
			 - 조회할 데이터가 너무 많으면 인덱스에 반복접근이 많아져서 부담된다.
			 - 클러스터는 관련 데이터를 물리적으로 모아두므로, 넓은 범위를 읽을 때 블록 접근 수를 줄이는 데 도움이 된다.

		 - 여러 테이블이 빈번히 조인될 때 사용
		  -> 정규화 때문에 분할된 반복 컬럼에 활용한다.

	* 클러스터의 특징으로 인한 설계 시 고려사항
		 - 검색은 빨라지지만 입력, 수정, 삭제는 느려질 수 있다. -> 테이블값이 변화가 거의 없고, 조회가 많은 테이블 위주로 사용하면 좋다
		 - 새로운 데이터를 넣을 때 어디에 넣어야 같은 그룹끼리 모일까를 고려해야 한다.
		 - DB는 단순히 빈 공간에 넣는 것이 아니라, 클러스터 구조를 유지해야 한다.
		 - UNION, DISTINCT, ORDER BY, GROUP BY가 빈번한 컬럼으로 고려한다.
			-> 즉 데이터를 묶거나, 정렬하거나, 중복을 제거하는 작업에서 고려된다.(두 개 이상의 테이블이 상호작용을 해야 할 일이 많은 상황에서 고려된다)

		EX.
		SELECT department_id, COUNT(*)
		FROM employees
		GROUP BY department_id;

		 -> department_id를 기준으로 데이터가 물리적으로 모여있다면 그룹화 작업이 유리할 수 있다.
		
		EX2.
		SELECT *
		FROM orders
		ORDER BY order_date;

		-> order_date 기준으로 데이터가 어느정도 모여있으면 정렬 부담이 줄어들 수 있다.

		하지만 무조건 적용되는 것은 아님
		해당 컬럼으로 조회, 정렬, 그룹화가 자주 발생하는지 확인해야 한다.

		 - 수정이 자주 발생하지 않는 컬럼이 좋다.
			 -> 클러스터 기준 컬럼은 자주 바뀌지 않는 것이 좋다. (ex. 회원 id)

		 - 단일 테이블 클러스터링 vs 다중 테이블 클러스터링
			(1). 단일 테이블 클러스터링
				- 하나의 테이블 안에서 특정 기준으로 데이터를 모아 저장하는 방식
				- 아래의 예시는 주문일자 기준으로 모은다.
				ex. order 테이블
				-> 2026년 1월 주문
				-> 2026년 2월 주문
				-> 2026년 3월 주문

			(2). 다중 테이블 클러스터링
				- 여러 테이블을 같은 기준으로 묶어서 저장하는 방식

				ex.
				customer_id = 1
				-> customer의 고객 1의 정보
				-> orders의 고객 1의 주문정보

				customer_id = 2
				-> customer의 고객 2의 정보
				-> orders의 고객 2의 주문정보

				이와 같이 두 테이블의 정보가 밀접하게 저장된다.

	6. 물리 데이터 모델 구성하기
	 - 논리적으로 설계된 데이터를 실제 데이터베이스에 저장할 수 있도록 구체적으로 설꼐하는 작업
	 - 논리 데이터 모델이 "어떤 데이터가 필요한가"를 정의하는 단계라면,
	 - 물리 데이터 모델은 "그 데이터를 실제 DB에 어떻게 저장할 것인가"를 결정하는 단계
