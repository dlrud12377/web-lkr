1. 빌드와 배포의 구분
 - 빌드는 소스코드를 실행할 수 있는 상태로 변환하는 과정을 말한다.
 - 배포는 개발자 또는 사용자가 애플리케이션을 실행하거나 테스트할 수 있도록 다음과 같은 자원을 서버의 적절한 위치로 이동하는 작업이다.

[빌드는 소스코드를 실행 가능한 형태로 변환하는 과정이고, 배포는 빌드된 애플리케이션과 실행에 필요한 리소스를 실제 실행 환경에 적용하는 과정이다.]

2. 애플리케이션 배포 단위

1. jar(Java Archive) : JAR는 여러 Java 관련 파일을 하나의 묶음으로 포장한 파일
2. war(Web Archive) : 
 - 웹 애플리케이션을 배포하기 위한 묶음 파일
 - Servlet, jar 파일과 WEB-INF 폴더의 web.xml 파일 등으로 구성되며 웹 컨테이너에 배포되어 웹 애플리케이션 서비스를 제공
3. ear(Enterprise Archive) : 여러 JAR/WAR를 하나의 엔터프라이즈 애플리케이션으로 구성


3. 코드 인스펙션
 - 정적 테스트의 가장 일반적인 유형으로, 사전에 정의된 코드 작성 규칙(Rule)을 기반으로 소스코드를 점검하여 작성 규칙에 위반되는 소스코드를 추출하는 분석 도구

4. 지속적 통합(CI)
 - 개발 과정에서 변경된 소스코드를 지속적으로 통합하고, 빌드와 배포를 수행하여 프로그램의 정상 여부를 확인하는 활동이다.

5. 프로그래밍 언어별 빌드 방식
 - 컴파일 언어(C, C++) : 기계어로 변환되어 실행
 - 바이트코드 언어(Java, C#) : 바이트코드로 변해서 JRE가 실행
 - 인터프리터(JS, Python) : 한 줄씩 번역

6. Check Out과 Check In(기준 : 저장소)
 - check out : 수정할 파일을 저장소에서 가져오는 것(저장소 기준으로 정보를 반출)
 - check in : 반출했던 형상 항목을 변경한 뒤 다시 형상 리포지터리로 전송

7. 배포 유형 선택

긴급 적용   	장애나 오류 발생 시   	개발자가 직접 즉시 배포 또는 관리자, PL의 최소한의 확인만 수행
일반 적용   	 개발, 수정된 프로그램에 대한 일반적인 적용   관리자, PL 확인 및 배포 관리자 확인, 테스트 수행 결과물 확인
통합 빌드   주기적으로 전체 개발 내역을 확인·점검하는 경우(2주~1개월)   배포 관리자가 애플리케이션 전체 소스를 일괄하여 빌드·배포 후 점검 보고서 추출

8.코드 인스펙션 심각도
   ㄴ 필수, Blocker : 에러 발생 가능성이 매우 높거나 메모리 누수가 발생하느 코드로, 반드시 수정되어야 하는 위반 사항
   ㄴ 권고 상, Critical : 에러 발생 가능성이 높거나 일반적으로 수정되어야 한느 심각한 위반 사항
   ㄴ 권고 중, Major : 에러 발생 가능성이 있거나 수정을 권고하는 중요 위반 사항
   ㄴ 권고 하, Minor : 소스코드의 가독성, 유지보수성 향상을 위해 수정을 권고하는 위반사항
   ㄴ 정보, Info : 정보성으로 제공되는 위반 사항으로 개발자가 참고하여 적용할 수 있다.


9. 정적 분석과 동적 분석
정적 분석 : 작성된 소스코드를 실행하지 않은 상태에서 분석하여 코딩 오류, 성능 저하 가능성, 보안 취약점 등을 점검하는 도구
동적 분석 : 애플리케이션을 실제로 실행하면서 프로그램의 동작 상태를 분석


10.테스트 커버리지
 - 작성한 프로그램이 테스트를 통해 얼마나 실행되고 검증되었는지를 나타내는 정도

15.운영 환경 접근 전 확인사항

18.통합 빌드 실패 원인과 대응 
 - 전체 시스템에서는 "서로 다른 모듈들이 연결되므로" 라이브러리 버전 충돌, 모듈 간 참조 관계, 인터페이스, 전체 환경 설정에서 문제가 발생할 수 있다.

관련 문제

통합 빌드 결과가 다음과 같다.

Compile : SUCCESS


Test
Tests Run : 100
Passed    : 100
Failed    : 0


Coverage
UserService  : 95%
OrderService : 35%


Code Inspection
Blocker  : 0
Critical : 2
Major    : 9
Minor    : 20

프로젝트 기준:

Blocker  → 반드시 수정
Critical → 반드시 수정
Major    → 수정 권고
문제
테스트가 100% 성공했으므로 테스트가 충분하다고 판단해도 되는지 설명하시오.
 - 충분하다고 판단할 수 없다.
 - 테스트 100개가 모두 성공했더라도 전체 코드 중 일부만 테스트했을 가능성이 있다.
 - 커버리지가 35%이므로 상당한 코드가 테스트 과정에서 실행되지 않았을 가능성이 있다.

OrderService에 대해 추가로 필요한 조치를 작성하시오.
 - 커버리지가 낮음 -> 현재 테스트 케이스 검토 -> 테스트되지 않은 부분 확인 -> 다시 테스트 -> 커버리지 재확인

코드 인스펙션 결과를 근거로 빌드·배포를 계속 진행해도 되는지 판단하시오.
 - 현재는 그대로 진행하면 안된다.
Critical이 2건 존재하고 프로젝트 기준에서 Critical은 반드시 수정하도록 정의되어 있기 때문이다.
따라서 개발팀에 수정 요청 후 다시 코드 인스펙션을 수행해야 한다.

개발팀에 전달해야 할 내용을 구체적으로 작성하시오.
 - 전체 테스트 결과 : 100건 모두 성공
 - OrderService Coverage : 35% / 테스트 케이스 추가 필요
 - Critical 2건 존재
 - Major 9건 존재
 -> 수정 후 테스트 및 인스펙션 재수행 필요

테스트 결과와 테스트 커버리지의 차이를 설명하시오.
 - 테스트 결과 : 실제 실행한 테스트가 성공했는가?
 - 테스트 커버리지 : 테스트를 통해 프로그램 코드의 어느 정도가 실제로 실행되었는가?

19.배포 장애와 Rollback
rollback : 새롭게 적용한 변경 내용을 취소하고 이전 정상 상태로 되돌리는 것
 - 배포 장애가 생겼을 때 오류 발생 시 이전 버전으로 롤백
 - 롤백이 어렵다면 프로그램을 수정하여 재배포

20.운영·유지보수 조직으로의 이관

## (1) 운영 및 유지·보수 전환 기준을 정의한다.

신규 프로젝트 종료 후 운영 및 유지·보수로 전환하기 위한 **필수 산출물**을 정의한다.
- 화면 설계서
- 데이터 설계서
- 프로그램 설계서
- 소스코드
- 운영자 매뉴얼 등

 -> 장애가 발생했을 때 프로그램 구조, db 테이블, 설정, 기능 등을 확인 필요
 ->운영 및 유지보수에 필요한 문서와 Source를 전달해야 한다.


- 전환 수행 조직별 역할 및 책임 : 누가 무엇을 넘겨주고 누가 무엇을 인수할 것인지
- 전환 대상 : 어떤 시스템과 문서를 넘길 것인지
- 전환 일정 : 언제부터 언제까지 인수인계를 수행할 것인지
- 교육 및 인수인계 방안 : 운영 담당자가 시스템을 이해할 수 있도록 교육하는 방법
- 운영 주체 변경 시점 : 어느 시점부터 실제 운영 책임이 개발 조직에서 운영 조직으로 넘어가는지를 명확하게 정한다.
- 이슈 및 리스크 : 전환 과정에서 발생할 수 있는 문제를 미리 확인
- 체크리스트 : 전환 과정에서 빠뜨린 항목이 없는지 확인
